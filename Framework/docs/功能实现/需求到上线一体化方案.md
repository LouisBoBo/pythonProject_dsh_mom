## 0. 一句话

这是 **WorkBuddy 本仓的新功能**（`features/dev-pipeline` + `engine/app/dev_pipeline`）：**一张时间线式 pipeline 卡** + 一本 Epic 账本，把「需求 → 上线」串起来。  
用户在聊天里 **说一次需求即可开跑**；执行过程 **逐步展开、可折叠、可回看**；全部完成后 **汇总成败与链接**。  
**写码、审码、提交、部署仍用已经存在的能力**，本功能在后台 **新开** 各工位并 **把过程镜像进 pipeline 卡**；**禁止改现有四车道的行为、卡、API、持久化**。  
**禁止**做成第二个业务 Cordis 包，也 **禁止** 为了本功能去改 DSH 插件源码。

## 1. 先解决的两个疑问

### 1.1 已有「DSH Cursor 写码 / 提交 / 审核 / 部署」能不能复用？

**能复用，而且必须复用。** 复用的是 **能力与入口**，不是把四条车道并成一张万能卡。

| 已有能力 | 本仓位置 / 插件 | 一体化里扮演哪一步 | 怎么复用 |
|----------|-----------------|--------------------|----------|
| **Cursor 写码** | 宿主插件 `@zhongruan/dsh-cursor-coding`（Job 常见 `ccj-*`，配置 `~/.zhongruan/cursor-coding`）；本仓只做配置同步与只读 Job（`engine/app/cursor_coding_store.py`、`/api/cursor-coding/config`） | **步骤 5 写代码** | 编排器把已确认的 PRD + 实现计划交给 **插件已有入口**（聊天里唤起 / 约定文件 / 已有工具）。本仓 **只读状态、记录 job_id**。**不改插件源码** |
| **本机审码** | `features/code-review` + `engine/app/code_review/` → `mes_code_review_begin` | **步骤 7 复核** | 编排器 **新开** `mes_code_review_begin`（新 `callId`、新审码会话），范围尽量收窄到本 Ticket 改动 |
| **人触发提交** | `features/code-commit` + `engine/app/code_commit/` → `mes_code_commit_begin` | **步骤 8 提交** | **新开** 提交卡：选目录 → 勾选 → 门禁 → 人确认 → commit/push。模型仍不代 git |
| **一体部署** | `features/code-deploy` + `engine/app/code_deploy/` → `mes_code_deploy_begin` | **步骤 10 部署上线** | **新开** 部署卡；成败仍只认引擎探活，不认「是否重启 DSH」 |

**明确不再复用 / 不再作为主路径**

| 名称 | 原因 |
|------|------|
| **`cursor_dev`（旧旁路应用）** | 产品已换成 Cursor 写码插件；一体化 **禁止** 再 `spawn` / 再接线 `apps/cursor_dev` |
| **改 `code-dev` / `mes_code_dev_*` 当本功能的写码主路径** | `code-dev` 仍是四车道里的「本机写码」车道（沙箱 / HITL / 删除菜单等），**保持原样给现有用户用**。一体化写码主路径对齐 **Cursor 写码插件**。不得为了 pipeline 去改 `code-dev` 的 phase、SSE、`wb-cd-*`、冻结清单 |

**复用边界（硬）**

- 只允许：**调用已有 begin / 只读 Job / 只读配置 / 把 artifact 路径传给下一步**。  
- 禁止：共用 `callId`、共用 `wb-cd-*` / `wb-cc-*` / `wb-cr-*` / `wb-cdp-*`、改现有卡的 phase 机、把四车道合成一张卡、在 pipeline 里直接 `git commit` / `gh pr` / SSH 绕过现有门禁。

### 1.2 为什么在本仓做，而不是做成 / 焊进「插件」？

这里的「插件」容易混成三件事，先拆开：

| 大家口头说的「插件」 | 实际是什么 | 适不适合做「需求→上线」整条链 |
|----------------------|------------|--------------------------------|
| **Cursor 写码插件** `@zhongruan/dsh-cursor-coding` | DSH 生态包：聊天里改盘、过程回显、本机 Job（`ccj-*`） | **只适合做步骤 5（写代码）**。它不是审码/提交/部署/开 PR 的真相源 |
| **再做一个新的 DSH 市场包**（又一个正式 Cordis） | 和写码插件并列，装进 profile | **技术上能做聊天 UI**，但会变成第二个业务包，和现有提交/审码/部署抢入口，且本仓铁律禁止再堆业务正式包 |
| **本仓 WorkBuddy feature** `dev-pipeline` | `features/` + 引擎账本，经唯一 `mes-bridge` 热插拔 | **适合做编排整条链**：它能合法调用已有审/提交/部署，并交接写码插件 |

**插件不是做不到，是不该由「写码插件」一个人做完整条厂。**

写码用插件，只说明 **「改文件」这件事已经有专业工人**。一体化要的是 **车间主任**：贴图理解需求、读仓库、写计划、验收、再叫审码/提交/开 PR/部署。主任不该住在螺丝刀厂里。

```text
写码插件 = 螺丝刀（改盘）     ← 你已经有了，继续用，不改它
审码 / 提交 / 部署 = 已有工位  ← 都在本仓引擎里，不是写码插件里
dev-pipeline = 流水线主任     ← 新功能，必须能指挥所有工位
```

若把 10 步焊进 Cursor 写码插件，会出现四件具体坏事：

1. **职责撑爆**：插件今天只保证「确认后改盘」。焊上 PRD、验证命令、GitHub Token、SSH 部署后，**写码一升级就可能带崩上线**，也违反「新功能不影响现有」。  
2. **调用方向反了**：审码/提交/部署的 HITL、Job、探活都在 **本仓引擎**。插件要做完整条链，最后还是得 HTTP 调 WorkBuddy。与其让插件仓依赖本仓，不如本仓编排、插件继续只写码。  
3. **会重复造轮子或改旧功能**：插件里再做一套 commit/deploy，就和现有车道双轨；或者去改现有车道「顺便适配插件」，正好踩中「不要影响现有」。  
4. **分仓改不了**：本仓 Agent **不许改** DSH 插件源码。一体化若做在插件仓，本仓这边无法交付，只能停工等另一条线。

**什么时候才该动写码插件？**  
只当步骤 5 缺「接收外部 plan/PRD」这类 **写码入口** 时，由你在 **插件仓** 加一个小接口。那是写码插件的本职补强，不是把一体化搬过去。

**一句话**：写码插件 **能** 写码，**不必** 也 **不该** 承担需求→上线；本仓做主任，插件继续做改盘。

## 3. 隔离铁律（新功能不得影响现有）

本次是 **全新车道级编排能力**，不是给写码/审码/提交/部署「加几个按钮」。落地时必须同时满足：

### 3.1 禁止改动的现有面（冻结）

| 冻结对象 | 禁止做什么 |
|----------|------------|
| `features/code-dev`、`engine/app/code_dev/`、写码卡 `wb-cd-*`、`CD_UI_REV` | 改 phase、SSE、`live_text` 路由、brief 语义、HITL 开工条件 |
| `features/code-review`、`code_review/`、`wb-cr-*` | 改入口话术、path_ticket、报告形态 |
| `features/code-commit`、`code_commit/`、`wb-cc-*` | 改选目录 → 门禁 → 确认顺序；禁止模型代 git |
| `features/code-deploy`、`code_deploy/`、`wb-cdp-*` | 改 confirm / 探活验收 |
| `@zhongruan/dsh-cursor-coding` 及任何 DSH 插件 | 本仓不改一行 |
| `mes-bridge` 里现有四张卡 | 禁止合并、禁止共享 persist；**仅允许**加 **新的** pipeline 卡与独立 CSS 选择器 |
| 四车道契约冻结清单 | 未单独开需求、未改契约并 bump 对应 `*_UI_REV` 前，禁止动 |

| 项 | 约定 |
|----|------|
| feature id | `dev-pipeline` |
| 工具前缀 | `mes_dev_pipeline_*`（禁止复用 `mes_code_*`） |

### 3.3 改码自检（每次实施前勾）

```text
□ 本次 diff 是否只新增 dev-pipeline / 独立卡 / 独立测试？
□ 是否出现 code_dev / code_review / code_commit / code_deploy / 现有 Card 的行为改动？→ 必须拆出去，本功能不做
□ 是否改了 DSH 插件或 profile 再堆正式包？→ 禁止
□ 新 begin（新 callId）是否可能吞旧四车道 done？→ 禁止读写 wb-cd/cc/cr/cdp
□ 现有「单独说写码 / 审码 / 提交 / 部署」话术是否仍只进原车道？→ 必须保持
```

### 3.4 意图分流（避免抢走现有入口）

| 用户说法（示例） | 必须进 |
|------------------|--------|
| 「写码 / 改这个页面 / Cursor 写码」 | **现有** Cursor 写码插件 / 现有写码车道（**不是** pipeline） |
| 「审核代码 / 审码」 | `mes_code_review_begin` |
| 「提交代码 / commit / push」 | `mes_code_commit_begin` |

## 4. 写码执行器口径（替代 cursor_dev）

```text
用户 / 编排器
    → 本仓 dev-pipeline（账本、PRD、计划、验证命令、PR、串联）
    → 步骤 5：交接给宿主「Cursor 写码」插件（已有 HITL / Job / 过程回显）
    → 本仓只读 ~/.zhongruan/cursor-coding 或插件回写的 job_id
    → 步骤 6～10 继续在本仓编排（验证新做；审/提交/部署调已有车道）
```

| 口径 | 说明 |
|------|------|
| **真相源** | 改盘结果以 Cursor 写码插件 Job（如 `ccj-*`）为准；编排账本只存引用 |
| **Key** | 继续走本机 `~/.zhongruan/cursor-coding` + 配置中心已有同步；pipeline **不另造** 一套 Cursor Key |
| **本仓已有、可继续用的只读面** | `/api/cursor-coding/config`、资料库对 ccj 的只读回填；**只读、不改语义** |
| **插件缺口** | 若插件暂时不能吃「外部 plan.md」，P0 可在 **时间线步骤 5 内嵌确认** 同一段计划；缺口列在 §14，**不在本仓改插件补** |

## 5. 总体架构（双循环 + 编排层）

参照 Cole：**外层低频定方向，内层高频交付**；**写码前先写验证**；规划对话与写码对话分开。

```text
外层（每个 Epic 一次）
  1 贴图+文字 intake → 2 需求理解 PRD（只 what/why）
  → 架构 how（可选但大需求必做）→ 切 Ticket + 依赖图

内层（每个 Ticket 一遍）
  3 Prime 读库 → 4 规划实现（含验证清单）→ 5 写码（Cursor 插件）
  → 6 验证 PASS/FAIL → 7 复核（审码车道）→ 8 提交（提交车道）
  → 9 开 PR（本功能新建 code-pr 或 pipeline 内 PR 模块）
  → 10 部署（部署车道）
```

**分层（铁律）**

```text
聊天壳 mes-bridge
  · 新卡：DevPipeline 时间线（单输入开跑 · 逐步 SSE · 回执 · 折叠 · 总结果）
  · 旧四张卡：一字不改；pipeline 在后台新开工位，过程 **镜像** 到时间线，不要求用户切卡操作
        │ HTTP 127.0.0.1
引擎 engine/app/dev_pipeline/
  · Epic/Ticket 账本 · artifact · 步骤门禁 · validate runner · PR
        │ 只调用 / 只记录
已有：Cursor 写码插件 · code-review · code-commit · code-deploy
```

## 6. 对话体验：单输入、全程可见、自动推进（产品定稿）

### 6.1 用户侧目标（你要的「越流畅越好」）

| 目标 | 含义 |
|------|------|
| **一次输入** | 用户在 DSH 输入框发送：**文字 + 可选贴图**（原型、报错截图等）。不必再为每一步单独发指令、不必切到别的工具卡才能继续。 |
| **默认自动跑完** | 编排器按账本 **自动 advance**：上一步 PASS（或允许跳过）→ 自动进入下一步，直到全部完成或 **硬阻断**。 |
| **全过程可见** | **同一张 pipeline 卡** 内展示 1～10 步（含 Epic 外层步骤时一并展示）；当前步 **展开**，已完成步 **可折叠** 但摘要始终可见。 |
| **每步有回执** | 每一步结束有固定 **Step Receipt**（见 §6.3），不是只有聊天一句「好了」。 |
| **可回看** | 刷新、关窗后再开：按 `callId` + Epic 账本 **恢复时间线**；任意已完成步可展开看过程日志与 artifact 链接。 |
| **总结果** | 全流程结束（成功 / 部分成功 / 失败）后，卡片顶部或底部固定 **Run Summary**（见 §6.4）。 |

这与 Cole 的「一步一 skill」**不矛盾**：skill 仍是引擎里的执行单元；**用户只面对一条时间线**，不在对话里来回换 ten 种说法。

### 6.2 和「企业 HITL」怎么同时成立？

**流畅 ≠ 取消审计。** 原则是：

- **软步骤（默认零额外点击）**：需求 intake、理解 PRD、Prime、规划、自动验证、审码报告生成等——在 **已绑定 workspace**（配置默认目录或 Epic 首次解析成功）且 **无硬风险** 时，由引擎 **代签「pipeline 会话级授权」**（一次 begin 时用户在输入框发送需求 = 同意在本 Epic 内自动推进软步骤）。过程仍 **全量写入时间线** 与审计日志。  
- **硬步骤（改盘 / git / 远端）**：写码（Cursor 插件）、commit/push、开 PR、部署——仍须 **引擎可验证的 nonce**。  
  - **体验上**：不在 pipeline 外另开一张孤立的提交卡让用户找；在 **同一张时间线** 对应步骤块内嵌 **确认条**（或插件/车道返回的确认 UI **嵌入 iframe 区域 / 同步状态到 pipeline SSE**）。用户 **最多点一次「确认并继续」**，不必重复描述需求。  
  - **安全上**：禁止聊天纯文本 `confirmed=true` 绕过；nonce 仍由 UI 签发，只是 **嵌在 pipeline 步骤里**，而不是让用户离开对话去别的入口。

可配置（`dev_pipeline.require_hitl_steps`）：

| 模式 | 行为 |
|------|------|
| **enterprise（默认）** | 硬步骤必须内嵌确认；软步骤自动 |
| **strict** | PRD / 计划锁定也加一次确认 |
| **dev_lab** | 仅 commit / deploy / PR 硬确认（本机调试，禁止写进发版默认） |

**禁止**：为流畅而关掉提交/部署的 nonce；为流畅而合并四车道 persist（仍 `wb-dp-*` 独立）。

### 6.3 单张 pipeline 卡 · 时间线 UI（不写码阶段的交互规格）

```text
┌─ Run Summary（完成后置顶；进行中为进度条 + 当前步名）────────────┐
│ 状态：进行中 3/10 · 需求理解 ✓ · 当前：读库上下文 …                │
└──────────────────────────────────────────────────────────────────┘

▼ 1 需求采集          ✓  PASS   2.1s   [折叠]
    摘要：识别 1 张原型图 + 3 条功能点 …
    回执：raw_intake.json · 图 2 张
    [展开过程] → SSE 日志 / 澄清问答记录

▼ 2 需求理解          ✓  PASS   …
    回执：PRD-lite v1 · 验收标准 4 条

▶ 3 读库上下文        …  RUNNING
    过程：正在索引 frontend/src/router …
    （实时追加，类似写码 live_text，但 channel=dev_pipeline）

▸ 4 规划实现          ○  PENDING

… 10 部署上线

（失败时：该步 ✗ FAIL + 原因 + 「重试本步 / 终止 Run」）
```

**交互规则**

| 规则 | 说明 |
|------|------|
| **一步一块** | 每步独立 `<section data-dp-step="3">`；状态：`pending` / `running` / `pass` / `fail` / `skipped` / `waiting_hitl` |
| **默认折叠** | 已完成步 **折叠** 只露：序号、名称、状态、耗时、一行摘要、回执链接 |
| **当前步展开** | `running` / `waiting_hitl` / 用户手动展开的历史步 → 显示 **Skill** + **这一步在干什么** + **过程流** + **结果/详细结果** |
| **过程流** | 引擎 `GET /api/dev-pipeline/runs/{id}/stream`（SSE）；事件带 `step_id` + `phase`（`log` / `artifact` / `receipt` / `hitl`）；过程开头带 Skill 横幅（会做/不会做） |
| **与四车道镜像** | 后台仍新开 `mes_code_*` / Cursor 插件 Job；pipeline **订阅** 其 Job 事件（只读），**复制摘要** 到本步过程区，**不**改写码卡 `wb-cd-*` |
| **持久化** | `wb-dp-card:{callId}` + Epic 文件双写；刷新后时间线 **不空壳**（禁止只留总结果删掉各步过程） |

### 6.4 Step Receipt 与 Run Summary（固定字段）

**每步回执（Receipt）**——结束时写入账本并在 UI 展示：

| 字段 | 说明 |
|------|------|
| `step_id` | 1～10 或 `outer-arch` 等 |
| `skill_id` / `skill_title` | 本步专业 Skill（见 `skill_catalog.py` / `skills/dev-pipeline/`） |
| `status` | pass / fail / skipped / waiting_hitl |
| `started_at` / `finished_at` | 上海时区展示 |
| `summary` | 一行人话结论 |
| `result_detail` | 多行：状态 + 摘要 + PASS/FAIL 判定说明 + 证据行（用户可读） |
| `artifacts` | 如 `prd_rev`、`plan_rev`、`ccj-*`、`commit`、`pr_url`、探活 URL |
| `evidence` | `process_log`、`skill.flow_brief`、验证 exit code、审码 Blocker 等 |
| `child_ref` | 关联的后台 Job / callId（排障用，默认折叠） |

**总结果（Run Summary）**——全部 ticket 完成后：

| 字段 | 说明 |
|------|------|
| `outcome` | `success` / `partial` / `failed` |
| `epic_id` | 账本 id |
| `workspace` | 工程路径（脱敏规则同现有车道） |
| `highlights` | PR 链接、commit、部署入口、关键文件数 |
| `failed_steps` | 若有失败，列出步号 + 原因 + 是否可重试 |
| `report_path` | 可选：`system-execution-report` 落盘路径 |

### 6.5 编排行为（自动 advance）

| 事件 | 编排器行为 |
|------|------------|
| 用户发送需求（含图） | `mes_dev_pipeline_begin` → 建 Epic → **自动** 从步骤 1 开始 |
| 某步 PASS | 写 Receipt → SSE `step.receipt` → **自动** `advance` 下一步（无需用户再说话） |
| 某步 FAIL | 标记 Run 为 `failed` 或 `waiting_user`（配置）；提供 **重试本步**（新 Job，不吞旧过程） |
| 某步 `waiting_hitl` | 时间线内嵌确认；nonce 完成后 **自动** 继续本步剩余动作并进入下一步 |
| 用户中途说「停」 | 取消 advance；已完步保留可回看 |

主入口工具语义调整（相对旧版「向导式每步 HITL」）：

| 工具 | 语义 |
|------|------|
| `mes_dev_pipeline_begin` | **单输入开跑** + 创建时间线卡 |
| `mes_dev_pipeline_advance` | 一般由 **引擎自动调用**；Agent 仅在重试/跳步时显式调 |
| `mes_dev_pipeline_run_full_loop` | = begin + 自动 advance 直到结束或阻断（**不是** dark factory：UI 全程可见） |

### 6.6 与现有功能的关系（仍然不并卡）

- 用户 **只操作 pipeline 时间线**（+ 内嵌确认条）。  
- 四车道 / 写码插件 **仍在后台按原契约运行**；老入口「单独写码 / 单独提交」**行为不变**。  
- 若用户从 pipeline 点「在本步打开原卡排障」→ **可选** 深链新开对应车道卡（只读/排障，**不是**主路径）。

## 7. Cole Skills 是否有帮助？十步出错怎么还能「正确跑完」？

### 7.1 Cole Skills 对本项目 / 对 Agent 的价值

**有帮助，但只能当「说明书 + 话术模板」，不能当「流程引擎」。**

| Cole 做法 | 帮助在哪 | 本仓怎么用 | 不能替代什么 |
|-----------|----------|------------|--------------|
| 每步一个 `SKILL.md` | 边界清晰：何时触发、做什么、禁止什么 | 在 `apps/zr-workbuddy/skills/dev-pipeline/` **借鉴/改写**（对照 [coleam00/skills](https://github.com/coleam00/skills) 与 [文章思路](https://mp.weixin.qq.com/s/y5rbB_06IYKM2O6D0G75vw)）；DSH 对话里按需加载简介 | **PASS/FAIL 判定**、重试次数、advance 时机 |
| 双循环 + validation-first | 先定验收再写码；规划与实现分场 | 步骤 4 计划里写死验证清单；步骤 6 只认命令 exit code | 引擎跑测试、写 Receipt |
| `piv-validate` 只回 PASS/FAIL | 减少模型自嗨 | 引擎 `validate.py` 输出二值；UI 只展示结果 | — |
| `piv-fix-review-findings` 等修复 skill | 失败后有标准回路 | 映射到下面 **§7.3 修复边**（表） | 仍须 Job + 上限，防死循环 |
| 33 个 skill 懒加载 | 省 token | Agent 读 skill 正文；**编排以 `mes_dev_pipeline_*` + 账本为准** | 聊天里 Agent 说「完成了」不算完成 |

**对 Cursor/DSH 里干活的 Agent**：Skill 教 **别跳步、别 Bash git、失败调哪个工具**；**是否真的完成** 只看引擎账本里该步 `status=pass` 与 Receipt。

**实施建议**：从 Cole 仓库 **挑选** 与 10 步对应的 skill 复制进本仓后 **必读改写**（工具名改成 `mes_dev_pipeline_*` / `mes_code_*`、写上 WorkBuddy 门禁）。**禁止**把 33 个原文当唯一真相源而不读。

### 7.2 核心原则：流程正确性由引擎保证，不由聊天保证

```text
聊天 Agent + Cole Skill  →  建议、解释、帮用户看懂时间线
engine/dev_pipeline      →  状态机、前置条件、PASS/FAIL、重试、advance、Run Summary
各工位 Job               →  写码/审/提交/部署 的真实算数
```

**禁止**：某步失败后仍因 Agent 幻觉自动 `advance`。**必须**：账本该步 `fail` 或 `waiting_user` / `waiting_hitl`，SSE 推送，时间线停在该步或进入 **修复边**（§7.3）。

### 7.3 状态机与「修复边」（任一步出错后的标准出路）

每步在账本中有：`pending → running → pass | fail | waiting_hitl | waiting_user`。

**自动修复边（有上限，默认可见）**

| 失败步 | 典型原因 | 自动策略（默认） | 上限后 |
|--------|----------|------------------|--------|
| 6 验证 | 测试/lint 失败 | 自动回到 **5 写码**（带失败日志 + plan），再跑 6 | `max_fix_rounds`（如 3）→ `waiting_user` |
| 7 复核 | Blocker | 自动 **5 写码** 或 `piv-fix-review-findings` 等价回路 | 同上 |
| 8 提交 | 门禁 findings | 调已有 **提交→写码修复** 闭环，完成后 **仅重试 8**（不重头） | 同上 |
| 5 写码 | 插件 Job 失败 | 同一步 **retry**（新 child Job，过程追加不覆盖） | 达上限 → `waiting_user` |
| 9 开 PR | 分支已存在 / PR 已存在 | **幂等**：检测已有 PR → `pass` 并写 URL | 不可恢复错误 → fail |
| 10 部署 | 探活失败 | 可选 1 次 **restart 引擎** 后重探（配置开关） | → `waiting_user` |

**不可自动修（必须人）**：选错 workspace、Token 缺失、Git 无权限、用户 reject HITL → `waiting_user`，时间线展示 **原因 + 配置指引 +「重试本步」**。

**用户显式操作（不破坏已完步）**

| 操作 | 行为 |
|------|------|
| **重试本步** | 新 Job id；旧过程保留在时间线（折叠为「第 1 次尝试」） |
| **跳过本步** | 仅当 `dev_pipeline.allow_skip_steps` 含该步 + HITL 理由落盘 → `skipped`，advance（企业默认 **关** 跳过 8/9/10） |
| **终止 Run** | `outcome=failed`；已完步 Receipt 全保留 |
| **从第 N 步继续** | 账本 `resume_from_step=N`；1～N-1 须已为 pass/skipped |

### 7.4 每步「正确执行」= 前置条件 + 执行 + 可验证 PASS

引擎在 **进入** 每一步前做 **precondition check**（不过则不 running，直接 fail 并写原因）：

| 步 | 前置条件（示例） |
|----|------------------|
| 2 | 步骤 1 有 `raw_intake` 或等价 artifact |
| 4 | 步骤 3 有 `context_pack`；workspace 已绑定 |
| 5 | 步骤 4 `plan_rev` 已锁且含验证清单 |
| 6 | 步骤 5 pass 且有 `cursor_job_id` 或声明无代码变更 |
| 8 | 步骤 6 pass；7 无未 waive 的 Blocker |
| 9 | 步骤 8 pass 且有 commit hash |
| 10 | 步骤 9 pass（或配置允许无 PR 直 deploy）且 deploy 配置齐全 |

**PASS 判定优先机器、其次 HITL**：

- 6：`validate_commands` 全部 exit 0 → pass。  
- 7：审码报告 Blocker=0 或 waive nonce → pass。  
- 8：提交 Job 成功 → pass。  
- 其余步：artifact 存在 + 规则检查 + 必要时的确认 nonce。

### 7.5 「全流程跑完」的三种合法结局（不是只有 100% 成功）

| `outcome` | 含义 | 对用户 |
|-----------|------|--------|
| **success** | 当前 Ticket 1～10（及配置要求的步）均 pass | Run Summary 给 PR、commit、入口 |
| **partial** | 例如 1～8 pass，9 PR 失败 | 明确 **已交付代码未合入** + 失败步 + 一键重试 9 |
| **failed** | 在修复上限内未恢复 | 停在哪步、已产生哪些 artifact、建议人工介入 |

**企业默认**：不允许「静默 partial」——partial 必须在 Run Summary **标黄/标红** 并列出未完成步。

### 7.6 与「单输入、自动 advance」的关系

- **自动 advance 只在 `pass`（或显式 `skipped`）后触发**。  
- **fail / waiting_*** 停止 advance；时间线当前步展开并显示错误；后台 **可自动走修复边**（§7.3），修复成功后再 pass → 再 advance。  
- 用户 **无需再输入需求**；若需输入，仅是 HITL 确认或点「重试本步」。  

这样既满足流畅，又避免「某步错了还假装往下走」。

### 7.7 配置项（`dev_pipeline` 节选，写码时落地）

| 键 | 含义 | 建议默认 |
|----|------|----------|
| （会话）`integrated_flow_enabled` | **一体化开关**：对话顶栏「需求→上线 / 普通写码」，按 **DSH sessionId** 落盘；换会话默认关 | **关** |
| `max_fix_rounds` | 6↔5、7↔5 等自动修复轮数 | 3 |
| `step_timeout_sec` | 单步超时 → fail 可重试 | 按步区分 |
| `allow_skip_steps` | 允许跳过的步 id 列表 | `[]` |
| `on_step_fail` | `auto_fix` / `pause` / `fail_run` | 软步 `auto_fix`；硬步 `pause` |
| `require_steps_for_success` | 算 success 必须 pass 的步 | 1～10 可配置减 deploy |
| `idempotent_pr` | PR 已存在则 pass | true |

### 7.8 实施后如何验收「可靠性」

- 单测：状态机转移表（fail 不 advance；pass 才 advance；修复边达上限 → waiting_user）。  
- 集成：注入「步骤 6 故意 FAIL」→ 自动回 5 → 再 6 pass → 继续 7。  
- 回归：**现有四车道单独入口** 不受 pipeline 失败路径影响。

### 步骤 1 · 贴图输入需求

| 项 | 设计 |
|----|------|
| Skill | `req-intake-multimodal` |

| 项 | 设计 |
|----|------|

### 步骤 9 · 开 PR

| 项 | 设计 |
|----|------|

## 12. 分期（全做，但仍按增量，避免一次改爆现有）

「全做」= 目标范围包含 1～10 + 外层 + **§6 对话体验**；**实施仍按增量合入**，每一期 diff 只碰 `dev-pipeline` / `code-pr` / 新卡 / 新测。

| 期 | 范围 | 验收（且回归：单独走四车道仍与现在一致） |
|----|------|------------------------------------------|
| **P0** | ✅ `engine/app/dev_pipeline` · `features/dev-pipeline` · 时间线卡 · SSE · `test_dev_pipeline.py` | 单输入 begin → 1→2→4 自动 → **5 暂停**；**未改** 四车道代码路径 |
| **P1** | ✅ `prime.py` · `validate.py` · `confirm-step` · Run Summary · 时间线 HITL 按钮 | 1→2→**3**→4→5；确认写码后 **6**（validate_commands）→ **7** 交接；6 fail 可 auto_fix 回 5 |

## 13. 企业级非功能

- **HITL**：软步骤可会话级自动（§6.2）；**写码 / commit / PR / 部署** 仍 nonce，默认 **内嵌在时间线** 而非让用户另找卡。`dev_pipeline.require_hitl_steps` 可调 strict / dev_lab。  
- **可见性**：每步过程与 Receipt 落盘；SSE 脱敏；刷新可恢复（§6.3）。  
- **回环**：引擎只绑 `127.0.0.1` / localhost。  
- **密钥**：GitHub Token、Cursor Key 不进仓库、不进 SSE 原文。  
- **用量**：pipeline 自己的 LLM（理解/规划）走引擎账本；Cursor 写码用量仍归现有 Cursor/插件口径，**禁止叠记**。  
- **审计**：每步 `user_id`、nonce id、耗时、模型版本。  
- **可恢复**：`wb-dp-*` + Epic 文件；刷新只恢复本 pipeline 卡。  
- **配置**：`config.example.yaml` 增加 `dev_pipeline`（`validate_commands`、`pr_provider`、`require_hitl_steps`），不改现有 `code_dev` 默认值。

## 15. 明确不做什么

- 不恢复、不接线 **`cursor_dev`**。  
- 不把一体化做成 **DSH 市场第二个业务包**。  
- 不改 **DSH 插件源码**、不焊业务进 Studio。  
- 不把四车道 **并卡 / 并 persist / 并 Job 目录**。  
- 不为「方便」在 **pipeline 外** 偷偷 commit / 开 PR / 部署（步骤仍走对应工位 + nonce；只是 UI 内嵌在同一张时间线）。  
- 不做 **dark factory**（无人、不可见、无回执）；要做的是 **bright autopilot**（自动 advance + 全程可见 + 每步回执）。
