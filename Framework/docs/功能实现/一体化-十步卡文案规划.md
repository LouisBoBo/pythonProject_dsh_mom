# 一体化十步卡 · 文案规划（用户能懂 · 不失专业）

> **状态**：方案稿（先对齐文案，不写代码）  
> **产品口径**：测环境全自动；用户看过程流卡，应懂「现在在干什么 / 结果是什么」，不必懂引擎术语。  
> **原则**：对外白话专业；对内术语可留在日志/开发模式，默认折叠或不上主卡。

相关：`ops.py` STEP_DEFS · `skill_catalog.py` · 过程流 UI（`dev-pipeline.js`）

---

## 1. 现在的问题（用户视角）

| 现象 | 例子 | 用户感受 |
|------|------|----------|
| 步骤名夹杂实现细节 | 「写代码（Cursor 插件）」「读库上下文」「开 PR」 | 像给开发看的内部词 |
| Skill 条更像黑话 | 「PRD-lite」「Prime」「validation-first」「多模态」 | 看不懂还占版面 |
| 三问口语过土 | 「要做什么 / 怎么干 / 干成啥」 | 不专业 |
| 过程日志像排障 | `raw_intake`、`context_pack`、`prd_rev`、代签 nonce、记忆库噪音 | 像系统日志，不像进度说明 |
| 「上线」易误解 | 步骤 10「部署上线」 | 以为上生产；实际是测试环境 |

**目标版式（每张步骤卡）**

1. **步骤名**（短、固定、业务语言）  
2. **一句话进度**（本步在干什么 / 干完了什么）  
3. **结果摘要**（人能核对的成果，3～5 行内）  
4. **可选「详情」**（折叠：技术细节、Skill id、原始日志）

顶部时间轴只用「步骤名」；卡片正文不默认铺 Skill 英文名。

---

## 2. 文案总原则

1. **主语是业务，不是工具**：说「整理需求」「检查改动」，不说「PRD-lite」「Prime」「Cursor 插件」。  
2. **一步一名，全国通用**：10 个短名固定，不因实现换插件而改名。  
3. **完成态写结果，运行态写动作**：运行中「正在…」；完成后「已…（关键结果）」。  
4. **测环境说清楚**：步骤 10 与总标题避免单独「上线」二字暗示生产。  
5. **专业但不炫技**：可用「需求说明 / 实现计划 / 代码检查 / 合并请求」，避免「多模态 / validation-first / HITL」。  
6. **双轨**：`title_user`（界面）与 `title_dev` / skill id（内部）分离；默认只展示 user 轨。

## 3. 十步命名对照（建议定稿）

| 步 | 现名（对内可保留） | **建议用户可见名** | 一句话说明（可作卡片副标题 / flow_brief） |
|----|-------------------|-------------------|------------------------------------------|
| 1 | 需求采集 | **收集需求** | 汇总你发的文字和截图，作为本单依据 |
| 2 | 需求理解 | **整理需求** | 把需求写成清晰说明：改什么、怎么改、怎样算完成 |
| 3 | 读库上下文 | **了解项目** | 查看当前工程结构与相关文件，避免改错地方 |
| 4 | 规划实现 | **制定方案** | 列出拟改范围与验证方式，再开始改代码 |
| 5 | 写代码（Cursor 插件） | **编写代码** | 按方案在工程里实际修改文件 |
| 6 | 验证 | **自动验证** | 按清单跑检查，确认改动基本可用 |
| 7 | 复核 | **代码检查** | 审查本单改动风险，拦截明显问题 |
| 8 | 提交 | **提交代码** | 把通过检查的改动写入版本库 |
| 9 | 开 PR | **发起评审** | 创建合并请求，便于同事或流水线审阅（可选） |
| 10 | 部署上线 | **发布到测试环境** | 同步到测试环境并做探活，确认页面可访问 |

**总徽章建议**（可选，与测环境口径一致）  
- 现：「需求→上线」  
- 建议：「需求→测试发布」或保留「需求→上线」但副文案固定「终点：测试环境」

**时间轴短名**（更短时可再用）  
收集 → 整理 → 读项目 → 方案 → 写码 → 验证 → 检查 → 提交 → 评审 → 测环境

## 4. 卡片内字段改名（步骤 2 等「三问」）

| 现文案 | 建议 | 填写指引（给模型/引擎） |
|--------|------|------------------------|
| 要做什么 | **改动目标** | 一句话：改哪个页面/能力、用户要看到什么 |
| 怎么干 | **实现要点** | 2～4 条：动哪些层（界面/接口/配置），不写空话 |
| 干成啥 | **完成标准** | 可核对条目：点哪里、看到什么、怎样算过 |

步骤 4 计划区建议标签：  
**改动范围** / **验证清单** / **注意风险**（替代「validation-first」「场景 id」默认展示）

## 5. 每步「用户可见摘要」模板（规划用）

> 实现时：`summary` / 卡片主文走下列句式；`process_log` 技术句进折叠「执行详情」。

| 步 | 运行中 | 成功摘要（示例句式） | 失败时用户该看到 |
|----|--------|----------------------|------------------|
| 1 | 正在收集需求与截图… | 已收集需求（约 N 字，附图 M 张） | 未识别到有效需求，请补充说明或截图 |
| 2 | 正在整理需求说明… | 已锁定需求：{一句话目标} | 需求不够具体，无法继续（说明缺什么） |
| 3 | 正在了解当前项目… | 已了解项目（读取 N 处关键内容） | 工程目录无效或无法读取（给出处理提示） |
| 4 | 正在制定实现方案… | 已制定方案（拟改 N 处，验证 M 项） | 无法形成可执行方案 |
| 5 | 正在编写代码… | 已完成改动（N 个文件） | 写码未产生有效改动 / 任务失败原因 |
| 6 | 正在自动验证… | 验证通过（N 项）或 验证未配置（已跳过并标黄） | 哪条命令失败、退出码 |
| 7 | 正在检查代码… | 检查通过（无阻断项）或 发现 N 个问题 | 阻断项简述 + 是否已打回修改 |
| 8 | 正在提交代码… | 已提交（短 hash / 说明） | 提交失败原因（权限、冲突等） |
| 9 | 正在发起评审… | 已创建评审链接 或 本单跳过评审（测环境策略） | 无法创建的原因 |
| 10 | 正在发布到测试环境… | 测试环境已更新，探活通过（可附入口说明） | 发布失败或已回滚（原因一句话） |

状态词统一：完成 / 执行中 / 失败 / 跳过 / 已暂停（已有 `dpStatusLabel`，保持白话）。

## 6. 信息分层（卡怎么排）

```text
┌ 需求→测试发布 · 执行中 ─────────────┐
│ 进度 ●●●●●○○○○○  编写代码           │
├────────────────────────────────────┤
│ ⑤ 编写代码              执行中 12s  │
│ 按方案在工程里修改文件               │  ← 副标题（原 flow_brief 白话版）
│                                      │
│ 结果：已改 3 个文件（列表可展开）     │
│                                      │
│ ▸ 执行详情（默认折叠）               │  ← Job id / Skill / 原始日志
└──────────────────────────────────────┘
```

**默认隐藏（进折叠或开发开关）**  
- Skill 英文 id、`Skill` 标签条  
- `raw_intake` / `context_pack` / `prd_rev` / `plan_rev` / job_id  
- 「记忆库噪音」「runtime 注入」「代签」等排障句  
- Cole / validation-first / Prime / PRD-lite 等词

**默认展示**  
- 用户步骤名、白话副标题、结果摘要、失败原因、测环境相关结论

## 7. 实施范围（有代码时再动，本阶段只规划）

| 优先级 | 改什么 | 说明 |
|--------|--------|------|
| P0 | `STEP_DEFS.title` + 时间轴展示名 | 用户第一眼 |
| P0 | 步骤 10 / 总徽章与测环境口径对齐 | 消除「上生产」误解 |
| P0 | `skill_catalog` 的 `title_zh` / `flow_brief` 改白话 | 卡片副文与 Skill 条 |
| P1 | 三问字段标签 + 模型输出提示词 | 步骤 2 主内容 |
| P1 | `summary` / 关键 `_log` 用户句与技术句分离 | 主卡干净 |
| P1 | UI：Skill 条默认折叠；详情区收技术日志 | 少打扰 |
| P2 | 文案表单测（产品走读一单完整卡） | 定稿用词表 |

**不改**：10 步顺序与职责、全自动不停顿、部署探活逻辑（只改说法与展示分层）。

## 8. 用词禁忌 / 推荐

| 少用（默认界面） | 改用 |
|------------------|------|
| 多模态、识图引擎名堆砌 | 文字和截图 |
| PRD / PRD-lite | 需求说明 |
| Prime、读库 | 了解项目 |
| validation-first | 先定验证再改（或直接「制定方案」） |
| Cursor 插件、Job、HITL、nonce | 编写代码、任务 |
| 开 PR | 发起评审（括号可写「合并请求」） |
| 部署上线、上线成功 | 发布到测试环境、测试环境已更新 |
| raw_intake、context_pack | 需求原稿、项目了解结果 |
| 干成啥 / 怎么干 | 完成标准 / 实现要点 |

---

## 9. 验收（文案侧）

1. 不看技术背景的同事，能指出每一帧「现在在干什么」。  
2. 全程截图里**默认区域**不出现：Prime、PRD-lite、Job id、Cursor 插件、nonce。  
3. 步骤 10 文案明确是测试环境。  
4. 失败卡用业务原因，不单甩内部异常栈。  
5. 开发仍能在「执行详情」里看到原 skill id / 日志（便于排障）。

---

## 10. 一句话

十步卡优化的是**对外说明书**：步骤名与摘要用业务汉语讲清进度和结果；专业细节收进折叠，测环境说满，不把流水线黑话摊在用户脸上。
