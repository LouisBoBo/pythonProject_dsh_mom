# 桌面应用版本升级方案（检查 + 全量下载 + 人确认拉起安装包）

> **状态**：2026-09-22 定稿实施（一期）。  
> **决策人确认**：落点 = WorkBuddy 桌面壳本体（否决插件形式）；一期 = 检查 + 全量下载 + 人确认后拉起现有安装包；平台 = Windows + macOS 一起；清单服务 = 与公司私有插件市场同一台服务器、**另起路径不共用**；版本口径 = **用户只看安装包版本号**。  
> **发版怎么打成功（运维口令 + 包内启动/知识库/桌面壳契约）**：见 [桌面打包发版流程与规则.md](../宿主与运维排障/desktop-packaging-release.md)（2026-10-14：PATH、侧栏、功能开关、relink、离线更新插件、写码 zod dist）。

---

## 0. 为什么不是插件

| 候选形态 | 否决原因 |
|----------|----------|
| WorkBuddy `features/` | 禁止 `import` npm；无法杀安装树、跑 NSIS、替换 Electron + 内嵌 Python/Host |
| DSH 生态插件（插件中心） | 升的是宿主 Profile 里的包，不是 `ZR WorkBuddy.app` / 安装目录；铁律禁止第二个业务 Cordis 包 |
| 引擎 `engine/` 下载执行 | 引擎跑在安装目录的内嵌 Python 上，**不能运行中覆盖自己和父进程** |
| 公司 DSH 插件市场通道 | 市场只服务 Cordis/Skill 目录；一体包是 GB 级 NSIS/zip，通道分开 |

升级是**整包替换安装目录**的产品能力，只能由桌面主进程（Electron main）承担下载、校验、退出、拉起安装程序。

## 1. 总体链路

```text
账号菜单「检查更新」（mes-bridge 设置页，只展示与确认）
        │  preload IPC（contextBridge，不暴露 Node API）
        ▼
Electron 主进程 desktop/main.js + desktop/lib/self-update.js
        │  1. check-update   拉 latest-<platform>.json，semver 比较
        │  2. download-update 全量下载到临时目录，进度事件回渲染层，sha256 校验
        │  3. install-update  人点「安装并退出」→ 拉起安装包 → app.quit()
        ▼
现有安装程序（NSIS / Mac zip）
        │  NSIS customInit 已会按安装路径杀残留、跳过旧卸载器；persist 回填 Key 与后装 features
        ▼
发版侧 scripts/lib/package_desktop.py
        └─ 打完包写出 release/latest-windows.json / latest-macos.json（版本、文件名、sha256、大小）
```

**分工边界**：桌面壳做升级执行；mes-bridge 只做 UI；引擎只提供 `/api/about`（产品名）；`features/` 与 DSH 插件**一律不参与**。

## 2. 更新清单（与公司市场同服、另起路径）

- 服务器：与公司私有插件市场同一台（`http://175.178.238.31`），**另起路径** `http://175.178.238.31/workbuddy-desktop/`，不共用 `dsh-plugins/` 目录。
- **服务器侧已就绪（2026-09-22）**：宝塔 nginx extension `…/extension/175.178.238.31/workbuddy-desktop.conf` → alias `/www/wwwroot/workbuddy-desktop/`；`.json` 禁缓存 + CORS，`.exe/.zip/.dmg` 强制下载；已回归验证 `/dsh-plugins/` 不受影响。
- **打包成功必须自动上传**（2026-09-23）：`package_desktop.py` 收尾调用 `upload_desktop_feed.py`（scp）；上传失败 = 发版失败。远端安装包最多保留 **2** 个版本。凭据见 `apps/zr-workbuddy/config/desktop-upload.env.example`。
- 文件名按平台分：**`latest-windows.json`**、**`latest-macos.json`**。两台打包机各自产出、各自上传，**不需要合并**，避免互相覆盖。
- 客户端默认地址写死在 `desktop/lib/self-update.js` 的 `DEFAULT_FEED_BASE`；可用环境变量 `WORKBUDDY_UPDATE_FEED_BASE` 覆盖（仅运维/调试，不发版默认）。

清单格式（打包脚本生成，**打包成功后自动 scp 上传**；勿再依赖人工复制）：

```json
{
  "product": "ZR WorkBuddy",
  "platform": "windows",
  "version": "0.2.27",
  "publishedAt": "2026-09-22",
  "notes": "一句话更新说明（打包时 WORKBUDDY_UPDATE_NOTES 传入）",
  "artifact": {
    "file": "ZR WorkBuddy-0.2.27.exe",
    "sha256": "<小写 hex>",
    "size": 123456789
  }
}
```

- 下载 URL 由客户端用 `feedBase + artifact.file` 拼出；**禁止**清单里写绝对 URL 指向别的 host（客户端会拒绝）。
- macOS 产物为 zip（与现行发版一致；dmg 不参与自动升级）。

## 3. 版本口径（用户只看安装包号）

- 比较与展示都以 **`desktop/package.json` 的 version**（= 安装包号，`app.getVersion()`）为准。
- 「检查更新」弹窗在桌面壳内**只显示安装包版本号**；引擎 `VERSION`（产品号）不再出现在该弹窗，避免「界面 0.4.1、包 0.2.26」两套口径。
- 有新版本时弹窗为信息表版式：当前版本 / 最新版本 / 安装包名 / 大小 / 发布日期 / 更新说明，按钮「下载并安装 / 稍后」；下载中显进度条，就绪后「安装并退出」。
- 浏览器/开发壳（`:3081`）没有桌面对象：保持现状提示「当前为浏览器/开发壳」，**不给开发模式做自动升级**（开发走 SVN Update）。
- semver 比较只看数字段（`0.2.27 > 0.2.26`）；`latest <= current` 即「已是最新」。

## 4. 一期行为（本方案实施范围）

**Windows**

1. 「检查更新」→ 拉 `latest-windows.json` → 有新版本：信息表展示 当前版本 / 最新版本 / 安装包名 / 大小 / 发布日期 / 更新说明 + 「下载并安装 / 稍后」。
2. 下载到 `os.tmpdir()/workbuddy-update/<version>/`，进度条实时刷新；完成后 **sha256 校验**（不符即删除并报错）。
3. 用户点「安装并退出」→ 主进程 `spawn` 安装包（detached）→ `app.quit()`。
4. 安装包 `customInit` 按安装路径杀残留（含市场 serve / 引擎 / 宿主）、跳过旧卸载器、覆盖安装；persist 自动回填。

**macOS**

1. 同上拉 `latest-macos.json`、下载 zip、sha256 校验。
2. 「安装并退出」→ `ditto -xk` 解压到临时目录 → Finder 选中新的 `.app` → 弹窗提示「拖进应用程序替换旧版」→ `app.quit()`。
3. 未公证，首次打开仍需右键「打开」（与现行手工升级一致）。

**无清单 / 离线 / 校验失败**：保持现有口径——「向管理员索取新安装包覆盖安装」，不阻断使用。

**每日首启自动检查（2026-09-22 追加）**

1. 桌面壳每天第一次打开（Asia/Shanghai 自然日，localStorage `wb-update-check-day` 记录）自动调 `checkUpdate`。
2. 只在拿到明确结果（`checked=true`）后才标记当日已查——离线/清单不可达时不标记，下次打开重试，全程静默无报错弹窗。
3. 有新版本：界面**左下角轻量提醒卡片**（无遮罩、不阻断操作）：圆点标题「发现新版本 vX」+「当前版本 vY，建议更新后继续使用。」+「稍后 / 升级」（**不含更新日志**）。
4. 「升级」→ 打开完整升级面板（信息表 + 下载 + 安装）；「稍后」/ Esc → 关闭，当日不再弹。
5. 仅桌面壳生效（`window.workbuddyDesktop` 存在且已登录）；浏览器/开发壳不弹。

## 5. 安全约束（与企业级安全底线一致）

1. **人确认**：「下载并安装」「安装并退出」都是渲染层按钮点击触发；主进程 `install-update` **只接受本会话内已下载且 sha256 校验通过的产物**（状态机保存在主进程，渲染层不能传任意路径）。禁止 Agent / 聊天一句话触发升级。
2. **来源校验**：三个 IPC 都沿用现有回环来源校验（`127.0.0.1/localhost/[::1]`）。
3. **下载约束**：仅 `http/https`；host 必须等于 feed base 的 host；重定向 ≤5 次；单包上限 3GB；超时 10 分钟。
4. **完整性**：`sha256` 必填，缺失即失败关闭（fail-closed）；校验不过立即删除临时文件。
5. **日志**：只记版本号 / 文件名 / 字节数；禁止回显带 token 的 URL。
6. **现行 HTTP 内网**的说明：清单与包同源同服，sha256 主要防「下载损坏 / 半截文件」；若服务器后续上 HTTPS，只改 `DEFAULT_FEED_BASE`，客户端代码不变。

## 6. 发版操作（管理员）

```bash
# 0) 一次性：配置上传凭据（勿提交）
#    cp apps/zr-workbuddy/config/desktop-upload.env.example \
#       apps/zr-workbuddy/config/desktop-upload.env
#    编辑 desktop-upload.env：填写 WORKBUDDY_DESKTOP_SSH_KEY=本机私钥路径

# 1) 各平台分别打包（禁止交叉打包）；打包即自动抬版本号，并写出清单 + **强制 scp 上传**
python scripts/lib/package_desktop.py            # 0.2.26 → 0.2.27，写 latest-*.json 并上传
#    更新说明：WORKBUDDY_UPDATE_NOTES="修复…" python scripts/lib/package_desktop.py
#    抬 minor/major：--bump minor / --bump major；指定版本：--set-version 0.3.0
#    重打同版本调试：--no-bump（--preflight / --skip-builder 本就不抬）
#    仅本机调试跳过上传：--skip-upload 或 WORKBUDDY_DESKTOP_SKIP_UPLOAD=1（禁止发版默认）

# 2) 上传由打包收尾自动完成（scripts/lib/upload_desktop_feed.py）
#    → scp 安装包 + latest-<platform>.json → /www/wwwroot/workbuddy-desktop/
#    → 远端只保留最近 **2** 个版本的安装包（更旧的 exe/zip + blockmap 删除）
#    → 探测线上 latest-*.json HTTP 200，失败则整次发版失败
#    版本号改动随下次 SVN 提交入库（desktop/package.json）
```

规则：`.cursor/rules/workbuddy-desktop-feed-upload.mdc`（LOCKED）。

客户端读不到清单时展示「当前已是最新版本（v…）」；有更大版本才进入下载/安装。

## 7. 明确不做（一期）

- 不上 `electron-updater` / 差量更新 / 静默替换（未签名 + 1GB 包，风险高；二期有签名与内网 CDN 再评估）。
- 不把安装包挂进公司 DSH 插件市场（`dsh-plugins/`）。
- 不在引擎进程里下载或执行安装包。
- 不给浏览器开发壳做自动升级。
- 不动 `features/`、不动任何 DSH 插件仓。
