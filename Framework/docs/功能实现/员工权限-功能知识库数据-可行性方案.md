## 1. 一句话

员工提问时过三道门，过了上一道才看下一道：

1. **功能权限**：这个功能能不能用（问数、写码、部署等）。已经有了。  
2. **知识库权限**：按文档勾。勾了的文档可以引用，没勾的不能引用。  
3. **数据权限**：只管控两项敏感数据——**物料采购单价**、**员工工资**。勾了才能看，没勾不能看。产量、工单等其它数据仍按问数功能开关。

小李问数开着，能问今天产量，文档只勾了《工艺规程》。他问采购单价或工资时看不到数；《薪酬制度》没勾，回答里也不出现这篇原文。小王勾了工资和《薪酬制度》，就可以看。

---

## 2. 三道门怎么判

```text
员工发出一句话
    → 第 1 道  功能开了没有
         关了：直接拒绝，不查数、不翻资料
    → 第 2 道  聊天壳调用本仓「文档引用」工具
         引擎只读已勾文档的正文，再交回模型
         没勾的文档：不读取、不进回答
         知识库插件不判断这人能不能看
    → 第 3 道  若答案会带上采购单价或员工工资
         没勾：单价从结果里拿掉，或工资请求不发出
         采购单上的其它字段仍可查
```

管理员默认可看全部文档、采购单价和员工工资。每次仍写审计。成员只看被勾上的。成员看不到「人员和角色」。

## 3. 现状（已经有什么）

| 层 | 现在 | 缺口 |
|----|------|------|
| 功能 | `auth/capabilities.py` 按人关掉 9 项：问数、PCB 工艺、写码、审码、提交、部署、需求到上线、视觉识图、连接配置。默认全开，只有名单里写明关掉才拒绝 | 规则保持，本方案不重做 |
| 知识库 | 侧栏知识库是宿主插件 `@zhongruan/dsh-knowledge`。它负责建库、导入、查看原文；会话挂上库之后会整库召回。超长正文会切成多条 `entries`（标题如「原名 (2)」） | 插件没有、也不加入权限。勾选必须做在本仓，不能和「整库挂载召回」并行 |
| 数据 | 问数不直接连库写 SQL。配置中心导入只读 OpenAPI 后，`ask_api_route.py` 把问句匹配到 **GET 接口** 再请求 | 对接的 MES 尚未单独提供采购单价、员工工资。开了问数的人能打到已导入的全部接口 |
| 人 | 本机账号，角色只有管理员 / 成员。人员页已能改功能开关 | 同一页还没有文档勾选，也没有单价、工资两项开关 |
| 审计 | `security_audit.append_audit` 已能追加事件 | 单价、工资、文档被拒或被允许，还没按这个口径记 |

结论：功能门禁可以原样沿用。单价和工资在本仓问数链路里做完。文档能不能引用也在本仓做完：插件只提供文档的上传和阅读，授权名单和过滤都在引擎。

## 4. 可行性结论

| 层 | 结论 | 原因 |
|----|------|------|
| 功能 | **已落地，本方案只复用** | 人员页开关和对话拒绝都在 |
| 数据 | **高，本仓可以做完** | 只管控两项。MES 用独立只读接口或固定字段名交出单价和工资后，引擎在组织回答前摘掉或拒绝 |
| 知识库 | **高，本仓可以做完** | 人员页按篇勾选。提问时引擎只读取已勾文档再交给模型。插件不增加授权逻辑 |

**建议**：数据两项和文档勾选都在本仓闭环，和人员页一起做。插件保持现在的上传、查看能力，不接权限接口。

## 5. 功能权限（沿用，不改规则）

保持现在的口径：

- 目录仍是上述 9 项。  
- 账号上的 `disabled_caps` 为空 = 全开。  
- 只有明确写进禁用名单才拒绝，并提示找管理员开通。  
- 未登录、查不到人、未知功能：维持现有防误伤，不在这里新加拦截。  
- 全局 `plugins.json` 停用的功能，全员不可用，与按人开关叠加。

「连接配置」仍是功能权限：能不能导入、修改接口。导入 MES 的单价、工资接口，不等于成员自动能看这两项，还要在人员页勾选。

## 6. 知识库权限

### 6.1 插件只做基本使用，权限只在本仓

两边分开，避免两套授权：

| | 知识库插件 | WorkBuddy |
|--|------------|-----------|
| 做什么 | 建库、导入、查看、修改、删除文档 | 「人员和角色」里按文档勾选；提问时决定能不能引用 |
| 不做什么 | 不保存谁能看哪篇，不读人员名单，不按人过滤 | 不重做一套文档编辑器，不另建向量库 |

人员页上的文档列表，来自插件里已经存在的知识文档（读取现有列表）。勾选结果只存在引擎的用户账本里。

### 6.2 授权单位是一篇文档

管理员在人员页看到文档列表。勾上的文档这个人可以引用，没勾的无权访问。

个人「资料库 / 我的空间」仍只属于本人，不进这份列表。

超长文件入库时会被切成多条（标题带「(2)」「(3)」）。人员页只显示一篇文档。勾一次，切出来的各条跟着这篇走，管理员不用逐条勾。

### 6.3 谁默认能看

| 人 | 规则 |
|----|------|
| 管理员 | 全部文档，不看勾选名单。用插件维护文档 |
| 成员 | 对话里只引用勾上的文档 |
| 新上传的文档 | 默认不勾 |
| 上线时已经存在的文档 | 同样默认不勾。管理员勾上之后才能被该成员引用 |

一个文档都没勾：回答不引用公司文档，并说明当前账号没有可引用的文档。

> **待拍板（2026-10-10）**：本表「默认不勾」与二期清单第 13 项「共享知识库 = 公司资料唯一版本、任意同事召回一致」冲突，建议改为**按库授权 + 按库类型定默认值**，见 §15.6。

### 6.4 引用怎么拦住

3081 的回答由聊天壳生成，引擎不会自动出现在每一句话前面。引用必须走一次工具调用，和问数相同：

```text
员工提问，需要公司文档
    → 聊天壳调用本仓工具（feature 只负责登记工具）
    → runEngine 到引擎
    → 引擎按当前登录人取出已勾文档（管理员视为全部）
    → 用插件现有的本地读取接口，只取这些文档的正文（含切片）
    → 按问句留下相关片段，返回给聊天壳
    → 模型只根据这次返回组织回答
```

约定：

1. 勾选名单在引擎用户账本里。关掉文档引用这个 feature，全员暂时不能引用，名单还在。  
2. 工具不进现有 9 项功能开关。能不能引用只看文档勾选。  
3. 没勾的文档不读取。一个都没勾：工具返回「当前账号没有可引用的文档」，模型不得改口去用插件整库召回。  
4. 只调用插件已经存在的列表和正文接口（前缀 `/knowledge-local/v1`）。不要求插件新增接口。开工时先核对真实的列表、读取路径；对不上就先不做人员页文档勾选，不用标题模糊匹配凑合。  
5. 同一库里，标题去掉末尾「 (2)」「 (3)」后相同的切片，算一篇。勾的是这一篇。**（2026-10-10 修正：授权锚点改为 `knowledge_documents.id`，不再靠标题归并，见 §15.2。）** 之后新切出的同名切片跟着这篇，不用再勾。同一库里两篇要分开授权时，上传用不同标题（插件允许同名，同名无法拆开授权）。

插件自带的「把整个库挂到会话上再自动召回」看不见勾选，挂上之后没勾的正文也会进对话。成员问答不使用会话挂载。成员不显示知识库侧栏，也不能把库挂到会话上。管理员保留侧栏，用来上传和维护文档。

成员会话若已经挂着库：文档引用工具仍然只返回已勾正文；同时提示管理员卸掉挂载。验收时成员会话必须是未挂载。卸挂载用插件现有能力；没有现成卸载接口就不新做，由管理员在插件里卸掉。

## 7. 数据权限

### 7.1 只管控两项

本期在对接的 MES 中增加两项敏感数据，人员页各一个勾：

| 勾选名 | 含义 | 没勾时 |
|--------|------|--------|
| 物料采购单价 | 采购物料的单价 | 单价不进入回答。采购单上的品名、数量等其它字段仍可查 |
| 员工工资 | 工资金额 | 不向工资数据发请求，回答里不出现工资金额 |

产量、工单、质量、设备、仓储等其余已导入接口保持现状：问数开着就可以查，不再按数据域分批授权。

### 7.2 MES 对接约定

这两项必须能被单独认出来，二选一：

1. **各自一个只读 GET**（工资推荐这条；单价若单独查询也可以）。  
2. **出现在已有接口的返回里，字段名固定**（例如单价字段、工资字段在对接时写死名称）。

字段名或 path 写在配置里，供引擎识别。方案不写死 MES 的真实字段名。夹在一张大表里、又没有固定字段名时，勾选无法稳定摘掉，对接不算完成。

配置形状（写在 `config.yaml`，示例只放空值）：

```yaml
sensitive_data:
  purchase_unit_price:          # 物料采购单价
    path: ""                     # 独立只读 GET 时填写，例如 /api/purchase-prices
    fields: []                   # 嵌在其它接口返回里时填写固定字段名
  employee_salary:               # 员工工资
    path: ""
    fields: []
```

一项的 `path` 和 `fields` 都空，表示尚未接入。此时人员页的勾可以先保存。问到这一项时回答「尚未接入」，不从其它接口里猜测哪个字段是单价或工资，也不把整段采购单当成单价。配了 `path` 之后才按第 7.4 节决定发不发请求；配了 `fields` 之后才从返回里摘字段。验收要等 MES 把真实 path 或字段名填进配置，并且接口已能返回。

### 7.3 谁默认能看

| 人 | 规则 |
|----|------|
| 管理员 | 两项都能看 |
| 成员 | 默认两项都不勾。勾上才能看 |
| 新接入的单价、工资 | 不因为导入成功就自动放开 |

演示数据回退同样走这道门。成员没勾时，不用内置演示数字顶上单价或工资。

### 7.4 拦截点

在问数组织回答之前（`ask_api_route` / `resolve_ask_query` 取回结果、交给模型之前）：

- **工资没勾**：匹配到的是工资接口时，不发 HTTP。对话说明当前账号不能查看员工工资。  
- **单价没勾，且接口只返回单价**：不发 HTTP。  
- **单价没勾，但接口还返回采购单其它字段**：可以发请求；交给模型前去掉单价字段，回答里不出现单价。  
- **两项都勾了**：照常返回，审计记放行，不记金额原文。  
- 问数功能本身被关掉：走现有功能门禁，不再看这两项。  
- 问句没匹配到接口：维持现在的「说明查不到」，不改去打单价或工资接口。

追问用的短时记忆可以继续记接口，但每次组织回答前都要再查这两项勾选。不能因为上一问成功就放过下一问。

写码、审码、提交、部署不读这两项，本阶段不套这道检查。以后若有车道会替用户调用单价或工资接口，必须复用同一道检查。

## 9. 审计

复用 `security_audit.append_audit`。

| 事件 | 何时写 | 记什么 |
|------|--------|--------|
| 数据拒绝 | 成员要看没勾的单价或工资 | 用户 id、项（单价 / 工资）、path、结果=拒绝 |
| 数据摘除 | 采购单返回里去掉了单价 | 用户 id、项=单价、path、结果=已摘除 |
| 数据放行 | 勾了的单价或工资进入回答 | 用户 id、项、path、结果=放行 |
| 文档拒绝 | 本仓未把没勾的文档交给模型 | 用户 id、文档编号、结果=拒绝 |

不记金额、文档原文、口令、密钥。日志给管理员排查「谁被拒了」，不另做一套报表。

## 12. 验收

用两个成员账号。知识库里至少有两篇文档。单价和工资的端到端验收，等 MES 的 path 或字段名写入配置并且接口能返回之后再做。

1. 关掉小李的问数：问产量被功能门禁拒绝，业务系统无对应请求。  
2. 工资或单价的 `path`、`fields` 都还空着：问工资或单价时回答「尚未接入」，不把别的接口返回当成这两项。配上真实 path 或字段名之后再测下面两条。  
2b. 打开小李的问数，两项数据都不勾：问产量仍能返回；问工资不发工资请求；问采购单时回答里没有单价，品名和数量还在。  
3. 只给小李勾上「物料采购单价」：他能看到单价；工资仍被拒绝。没勾的小王仍然看不到单价。  
4. 管理员能看到单价和工资，审计里有放行记录，记录里没有金额原文。  
5. 小李只勾《工艺规程》：聊天通过文档引用工具拿到这篇正文；没勾的《薪酬制度》不在工具返回里，回答也不出现原文。同一篇被切成「(2)」「(3)」的，勾一次就全部可引用。成员看不到知识库侧栏，会话未挂载知识库。  
6. 新上传一篇文档：成员侧默认不勾，引用不到。插件本身不加任何授权开关。  
7. 成员账号看不到「人员和角色」，直接调保存接口得到 403。  
8. 审计里能按人查到拒绝记录，正文里没有单价、工资和文档原文。

## 13. 风险

| 风险 | 处理 |
|------|------|
| 单价夹在大表里且没有固定字段名 | 对接完成标准就是独立接口或固定字段名。对不上就不算这两项已接入 |
| 摘字段时漏掉同义字段（单价、含税价、price） | 配置里列出要摘的字段名，验收用真实返回抽查 |
| 会话仍挂着整库，没勾的正文被插件自动召回 | 成员不提供挂载入口。验收时成员会话必须未挂载。已挂上的由管理员卸掉；文档引用工具本身仍只返回已勾正文 |
| **项目级挂载整库自动召回（前文漏项）** | **按目录生效，没有会话可卸**：成员工作区命中该目录即整库召回，勾选被绕过。补法见 §15.4 |
| 插件列表或读取接口和文档不一致 | 核对 `/knowledge-local/v1` 现有路径。对不上就停文档勾选，不做标题猜测 |
| 成员从知识库侧栏直接打开没勾的文档 | 成员不显示知识库入口。管理员仍用侧栏维护文档 |
| 上线后成员暂时引用不到已有文档 | 按「没勾选无权访问」。管理员勾上才开放 |
| 用提示词代替拦截 | 不允许。工资在发请求前拒；单价在交给模型前摘掉；文档在交给模型前按勾选读取 |
| 管理员查看没有痕迹 | 管理员放行也记审计，只是不拦 |

### 15.5 结论

三道门里，功能门与数据门能落地，是因为拦截点在本仓引擎（工具注册处 / 发 HTTP 前）；知识门迟迟未动，是因为拦截点原先在插件侧。**把拦截点搬进本仓（引擎直读库 + 授权名单仍存 `users.json`）之后，知识门与另两道门同构**——按篇授权、默认不给、审计记账，其余章节不变。若不走直读，唯一替代是接受「聊天壳必须常开」，不建议。

### 15.6 修正四：授权粒度与默认值——建议**按库**，而不是逐篇逐人（**待拍板**）

**先说一处口径冲突（本仓文档内部）**：

| 出处 | 口径 |
|---|---|
| 二期清单 §13「共享知识库」为什么做 / 验收 | 公司资料**唯一版本**、**任意同事问同一问题召回来源一致** → 隐含**默认全员可见** |
| 本方案 §6.3 | 成员**默认零文档**（新上传不勾、上线前已存在的也不勾）→ 默认**全员不可见** |

两者并列会让第 13 项做出来也用不起来：管理员要为每个人、每一篇逐个勾。

**建议改法：粒度从「逐人 × 逐篇」降到「按库」，默认值按库的类型给。**

| 库 | 默认值 | 授权方式 |
|---|---|---|
| 公司库（工艺 / 口径 / 制度） | **默认可见** | deny-list：只把少数敏感篇标为受限 |
| 客户资料库 / 敏感库 | **默认受限** | allow-list：整库授给需要的人 |
| 同库内混放敏感件 | 例外 | 仅这类才需要逐篇 |

依据：`knowledge_bases` 表**本来就有**（现 2 个库：默认知识库 / 测试知识库），按库授权与现有数据模型天然对齐；方案稿 §14 把「按知识库整库勾选」列为不做，**这一条建议反过来**——按库勾选的维护量比逐篇低一个数量级，且在文档数从 2 篇涨到几十上百篇时不会失控。

**风险与缓解**：公司库默认可见，意味着新上传文档立刻全员可检索；若误传薪酬 / 合同即事故。缓解：上传后先落「待定级」，定级为公司库才转全员可见，定级为客户库则转受限。定级是**每篇一次**，不是每人每篇。

### 15.7 修正五：「封锁项目级召回」不是本仓能做的小活（**修正 §15.4 的估时**）

挂载记录在插件库（`knowledge_mounts`），召回动作发生在**宿主进程**。本仓（引擎）既拦不到宿主注入，也不该去改插件——所以 §15.4 我按「半天」估是不准的。真实出路只有四条：

| 出路 | 做法 | 代价 |
|---|---|---|
| A. 插件按身份过滤挂载 | 插件读人员名单，成员身份不注入 project 挂载 | 需要插件仓配合，**破「插件不接权限」的定调**；但这是唯一干净的做法 |
| B. 宿主侧不注入 | 宿主知道当前用户角色（3081 已有 `authUser.role`），成员身份下不注入 project 挂载 | 属宿主侧改动，须走 Studio 插件中心的既有边界 |
| C. 部署约定 | 公司机器上**不建** project 级挂载，只用会话级 | 靠纪律不靠代码，无法自证；成员换工作区即失效 |
| D. 成员独立 profile | 成员用独立 profile 与独立 knowledge.sqlite | 权限边界 = 文件边界，最干净；但部署与升级成本最高 |

**建议 A**：定调里的「插件不接权限」本意是插件不做**逐人逐篇的授权判定**；按身份决定「要不要注入挂载」是**召回开关**，不是授权判定，不违背该定调。

### 15.8 修正六：直读 SQLite 的健壮性（已实测，非推演）

| 项 | 实测结果 | 结论 |
|---|---|---|
| 日志模式 | `journal_mode = wal` | 需要处理 WAL 与共享内存文件 |
| 当前 WAL 状态 | `-wal` = **0 字节**，`-shm` = 32768 字节 | 当前无未落盘写入 |
| 模拟宿主未运行（只复制主库、不带 `-wal`/`-shm`） | `mode=ro` **可读**，`immutable=1` **也可读**，文档数一致 | 有可用的降级路径 |

**但降级必须保守**：副本读法会丢掉尚未 `checkpoint` 的写入，出现「刚设为受限的文档被读成未受限」的**陈旧窗口**。权限判定上的陈旧是**漏放**方向（比误拦更危险）。因此：

1. 主路径：`mode=ro` **直连主库**取实时状态；
2. 降级：仅当直连失败时才读副本；
3. **降级期间保守拒绝**（返回「知识库引用暂不可用」，不引用任何正文），不得因为读不到而放行；
4. 直连与降级都写审计，便于排障。

### 15.9 修正七：三道门整体是否偏重——建议知识门先做粗版

50 人、单客户内部场景下，功能门 + 数据门（两敏感项）已覆盖主要需求。知识门若一上来就做「逐人 × 逐篇矩阵 + 上传定级 + 切片归并」，投入产出比偏低。建议第一期只做：**按库授权（§15.6）+ 敏感篇例外 + 文档引用工具 + 审计**；逐篇矩阵留到多客户线（新增项 12 / 14）。
