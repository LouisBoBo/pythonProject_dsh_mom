# 共享知识库方案

> **状态**：**P0 已落地 · 傻瓜式自动接入**（2026-10-12）  
> **一句话**：公司资料一份中央库；成员只写本机、可读公司；**管理员上传时二选一**（本机私用 / 公司共享），避免「一上传就全员可见」再靠事后 ACL 补救。  
> **本体**：仍用宿主插件 `@zhongruan/dsh-knowledge`（**1.0.7+** 上传目标选择），不自研 RAG、不把知识库做成 `features/`。  
> **入口**：产品入口 `http://127.0.0.1:3081`；中央库另有一台常开知识服务（见 §3）。  
> **本仓落点**：`engine/app/company_knowledge.py`、`/api/company-knowledge/*`、feature `company-knowledge`（`mes_company_knowledge`）；  
> **交付**：`apps/zr-workbuddy/config/company-knowledge.env`（gitignore）+ `ensure_company_knowledge.py`，经 `ensure_runtime` / 桌面启动自动合并；**员工换机零手改**。

## 1. 产品口径（已拍板）

| 角色 | 上传 | 访问 |
|------|------|------|
| **普通用户（成员）** | **只能**上传**本机知识库**；仅本机使用，不进公司库 | 本机库 + **公司共享库（只读）** |
| **管理员** | 上传时**必须显式选择目标**：**本机知识库** 或 **公司共享知识库** | 本机库（私用）+ 公司共享库（维护 / 检索）；公司库多人可读 |

### 1.1 为什么管理员也要本机库

管理员往往是公司领导，手里会有：

- **未定稿 / 敏感草稿**（薪酬口径、未公开客户合同、内部讨论稿）  
- **已定版、应全员可见**的工艺 / 制度 / 客户资料  

若管理员「一上传就进公司库」，再靠事后逐人/逐篇收权限，**维护成本远高于上传时选一次目标**。  
因此定稿：**进公司库 = 管理员主动选择「公司共享」**；默认不得静默进公司库。

### 1.2 口径细则

1. **公司共享库** = 全公司唯一版本；任意同事问同一问题，召回来源应一致。  
2. **本机知识库** = 个人 / 领导私用草稿与资料；不参与「公司唯一版本」，不跨机同步。  
3. **上传目标只在写入时区分**；已进公司库的文档若要「收回只剩本机」，本期不做自动搬迁（需管理员在公司库删除 + 本机另存，或后续另开「下架」能力）。  
4. **资料库**（`space/`）仍与知识库分离。  
5. 公司库内再细分「谁能看哪类敏感篇」属二期 **14**；本方案用「上传时是否进公司库」把绝大多数误伤挡在门外，降低对细粒度 ACL 的依赖。

### 1.3 上传交互（管理员）

```text
管理员点「导入 / 上传」
  → 必选目标（不得有隐含默认进公司）：
       ○ 本机知识库（仅本机，其他人不可见）
       ○ 公司共享知识库（全员可检索；须二次确认文案）
  → 选本机：写入本机 sqlite
  → 选公司：写入中央库（须写权限 token）；成功后提示「已对公司可见」
```

成员上传：**无目标选择**，固定本机；UI 不出现「公司共享」选项。

## 2. 可行性结论

| 项 | 结论 | 依据 |
|----|------|------|
| 公司唯一库 + 多人读 | **高 · 插件已具备** | 中央 `local + exposeApi`；读侧 `remote` 或只读 API |
| 成员只写本机 | **高** | 成员侧栏 `backend: local` |
| 管理员本机写 + 公司写 | **中 · 要拼装** | 插件单实例 **local / remote 互斥**；不能开箱同连接双写 |
| 成员读公司 | **中 · 要拼装** | 同上，P0 用只读旁路 |

**定稿策略**：

- **P0**：中央库 + **上传目标选择**（管理员）+ 成员本机写 + 全员读公司走旁路/写公司走中央 API。  
- **P0.1（已落地 · 1.0.9+）**：**仅管理员**自动召回同时合并「本机挂载 + 公司共享」；成员自动召回只含本机，查公司库用 `mes_company_knowledge`。写公司仍仅管理员显式选择。  
- **P0.2（已落地 · 1.0.10+；侧栏只读 2026-10-13 对齐）**：侧栏「共享知识库」**全员可见只读**（带 **共享 / 免挂载**）；文档范围受人员页「共享知识库召回」白名单约束。管理员可在侧栏 **新建 / 导入 / 删除**（删除同步清中央库）；成员不可写公司库，召回仍可用 cite / `mes_company_knowledge`。本机库上传目标选择逻辑不变。  
- **P1（可选深化 · 插件仓）**：真·双后端 remote 并存、拖拽写目标与库树完全一致（当前用引擎旁路列表已满足侧栏可见）。

相对「管理员只能写公司」的旧口径：管理员双写目标使 **P1 双后端优先级升高**（领导日常也在本机 3081 办公，不宜强迫整机切 remote）。

## 3. 拓扑

```text
┌─────────────────────────────────────┐
│  公司知识服务（常开一台）              │
│  dsh + @zhongruan/dsh-knowledge       │
│  backend: local + exposeApi           │
│  = 公司共享知识库真相源               │
│  仅「目标=公司共享」的写入进入这里     │
└─────────────────┬───────────────────┘
                  │ HTTPS（须反代）
      ┌───────────┴────────────────────────┐
      │                                    │
┌─────▼──────────────────┐    ┌────────────▼─────────────────────┐
│ 管理员客户端              │    │ 普通用户客户端                      │
│ 本机库 = local            │    │ 本机库 = local（唯一上传目标）      │
│ 上传：二选一              │    │ 公司库 = 只读旁路                   │
│   · 本机 → 本机 sqlite    │    │ 无「公司共享」上传选项               │
│   · 公司 → 中央 API(写)   │    └──────────────────────────────────┘
│ 公司库读：旁路或双后端    │
└──────────────────────────┘
```

### 3.1 中央机（公司共享库）

| 配置项 | 值 | 说明 |
|--------|-----|------|
| `backend` | `local` | 真相源 |
| `databasePath` / `connectionPath` | 固定公司路径 | 备份按此文件 |
| `exposeApi` | `true` | 对外 API |
| `apiToken` | ≥24 位 | 不进仓库 |
| `extractionEnabled` | 默认 `false` | 与预装方案一致 |

该实例是 central server，**禁止**再切成 `backend: remote`。

### 3.2 管理员（日常在本人电脑）

- 默认连接保持 **本机 local**（草稿、私用资料）。  
- 选择「公司共享」上传时：走中央 **写 API**（管理员持有 `write`/`admin` token），**不**把整个侧栏切成纯 remote（避免丢失本机库）。  
- 也可在中央机上直接维护公司库（运维补位），但不替代「本机上传时选目标」的主路径。

### 3.3 普通用户

- 侧栏：`backend: local`，上传固定本机。  
- 读公司：§4 只读旁路。  
- 主连接不得改成纯 `remote`。

### 3.4 插件能力边界（取证）

- `backend`: `local` \| `remote`（**互斥**；无透明双写缓存）。  
- `remote` 须 `remoteUrl` + `remoteToken`（≥24）。  
- `exposeApi` 须 `apiToken`（≥24）。  
- Token：`read` / `propose` / `write` / `admin`（实例级，≠ WorkBuddy 按人 ACL）。  
- 插件 `shared` 路由 = **笔记分享**，不是公司知识库。

## 4. 读公司库 / 写公司库——P0 旁路

因 local/remote 互斥，P0 不要求侧栏同连接挂两套后端。

### 4.1 读（全员）

```text
提问需要公司文档
  → 本仓「公司知识引用」工具 → runEngine
  → 引擎用 read token 调中央 API
  → 片段回模型
```

1. 成员与管理员读公司均可用同一 read 通道（管理员另有写通道）。  
2. 中央不可达 → 「公司知识暂不可用」，禁止用过期本机副本当公司最新版。  
3. 本机挂载召回只覆盖本机库；P0 **不做**公司全文同步进各人 sqlite。

### 4.2 写公司（仅管理员 · 目标=公司共享）

```text
管理员上传且选择「公司共享」
  → 二次确认「将对公司可见」
  → 引擎或受控客户端用 write token → 中央导入/创建文档 API
  → 成功：提示已进公司库；失败：明确错误，不得假写入本机冒充已共享
```

1. 成员机 **不下发** write token。  
2. 选「本机」时 **不得** 调用中央写接口。  
3. 审计（若已有 `security_audit`）：记用户、目标=本机|公司、文档标题/id、结果；不记正文与 token。

### 4.3 P1 插件双后端（强烈建议）

插件仓交付「本机 provider + 公司 remote 并存」后：

- 侧栏同时展示本机库与公司库。  
- 上传目标选择与库树一致（拖到哪库 / 选哪目标即写哪边）。  
- 成员：公司库只读，无上传到公司。  
- 管理员：两库均可写（本机私用、公司共享）。  
- 引擎旁路可保留作验收或不绑宿主的读路径。

## 5. 与角色、权限方案的关系

| 层 | 本方案 | 员工权限方案 |
|----|--------|----------------|
| 上传目标（本机 vs 公司） | **本方案定稿**；管理员显式选择 | 不重复 |
| 公司库内敏感篇 / 按库 ACL | 不做；靠「不进公司库」降低误伤 | 共享库通后再做细收紧 |
| 功能 / 数据权限 | 不改 | 沿用 / 独立车道 |

**依赖**：本方案（13）→ 再做知识 ACL（14）。  
「上传时选本机」已挡住大部分「领导草稿误进全员」；细粒度 ACL 是补充，不是上传门禁的替代。

## 8. 验收

1. **唯一版本**：两成员同问已进公司库的文档，来源一致。  
2. **成员**：只能上传本机；写公司接口拒绝；可读公司已发布文档。  
3. **管理员选本机**：文档仅本机可见；其他账号不可检索到。  
4. **管理员选公司**：二次确认后进中央；成员只读可见；提示「已对公司可见」。  
5. **无默认进公司**：管理员上传流程不存在「未选目标却写入公司」。  
6. **本机隔离**：用户 A 本机文档用户 B 不可见。  
7. **中央不可达**：读/写公司失败有明确提示，不假成功。  
8. **密钥与日志**：无 token / 正文泄露。

## 9. 风险

| 风险 | 处理 |
|------|------|
| 管理员误选公司 | 二次确认文案写明「全员可检索」；P2 再加下架 |
| 无目标默认进公司 | **禁止**；验收第 5 条 |
| local/remote 互斥导致管理员难用 | P0 旁路写公司；P1 双后端优先排期 |
| write token 落在成员机 | 不下发；引擎校验角色 |
| 细 ACL 未做时公司库过宽 | 用「上传时选本机」控入口；进公司的默认全员可读（本方案接受） |
| 项目级挂载绕过后续 ACL | 见权限方案 §15.4 / §15.7 |

## 10. 明确不做

| 不做 | 原因 |
|------|------|
| 本仓自研 RAG | 铁律与预装方案 |
| 本机 ↔ 公司透明双向同步 | 插件故意不做 |
| 管理员上传默认进公司 / 无目标选择 | 维护成本与误伤 |
| 成员写入公司库 | 已拍板 |
| 用资料库或笔记 `shared` 冒充公司知识库 | 语义不同 |
| 共享库未通就先做逐人逐篇 ACL | 入口区分优先；ACL 在后 |
| 企业 SSO | 另案（二期 12） |

## 11. 配置与傻瓜式交付

### 11.1 员工 / 换机（不要手改 config.yaml）

1. 装 WorkBuddy 桌面包，或开发机 `host.sh wire` / `ensure_runtime --fix`  
2. 安装包/仓内已带 `company-knowledge.env`（发版机持有，gitignore）  
3. 启动时自动把空缺项写入本机 `engine/config/config.yaml`  
4. 刷新 **3081**；管理员账号上传可选「公司」，成员自动可读公司库  

破窗（本机不要公司库）：`WORKBUDDY_SKIP_COMPANY_KNOWLEDGE=1`。

### 11.2 发版机一次性（运维）

```bash
cp apps/zr-workbuddy/config/company-knowledge.env.example \
   apps/zr-workbuddy/config/company-knowledge.env
# 填入 READ_TOKEN / WRITE_TOKEN（与中央机 workbuddy-company-tokens.env 一致）
# 桌面打包会 assert 种子存在且 READ_TOKEN≥24
```

### 11.3 合并进 config.yaml 的形状（自动生成，勿要求员工填写）

```yaml
company_knowledge:
  base_url: "https://《中央机》:8093"   # 反代后的知识 API 根（无尾斜杠）
  api_prefix: "/knowledge-api/v1"
  read_token: ""          # 种子下发；≥24
  write_token: ""         # 种子可下发；引擎仍按 role===admin 门禁写
  knowledge_base_id: "default"
  timeout_ms: 10000
  verify_ssl: true        # 中央机自签证书时种子写 false
```

中央机插件（示意）：

```yaml
- id: knowledge
  name: '@zhongruan/dsh-knowledge'
  config:
    backend: local
    databasePath: !!js dshHomePath('knowledge/knowledge.sqlite')
    connectionPath: !!js dshHomePath('knowledge/connection.json')
    exposeApi: true
    apiToken: "《中央机本地密钥》"
    exposeWeb: true
    extractionEnabled: false
```

## 13. 一句话

**进公司库必须管理员显式选择；本机留给私用草稿（含领导）；成员只写本机、可读公司；P0 旁路读写公司，P1 插件双后端把「选目标」做进侧栏。**
