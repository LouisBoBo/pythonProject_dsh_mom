# 人员和角色维护 · 可行性实施方案

> **状态**：**P0 人员维护已落地**；**P0.5 人员引擎能力一键启停已落地**（2026-09-28，含防误伤加固）  
> **范围**：本机登录账号的**人员维护**（加人 / 停用 / 改角色 / 重置口令）+ **两个内置角色**（管理员 / 成员）+ **按人引擎能力**（问数/PCB/写码/审码/提交/部署等，默认全开；仅明确关掉才不可用，对话提示找管理员）  
> **入口**：产品入口 **`http://127.0.0.1:3081`** 账号菜单「人员和角色」（仅 admin）；引擎 **`:8000`** 侧栏同步有管理页  
> **实现**：`auth/capabilities.py`（默认放行）· `PUT …/capabilities` · `require_enabled` 叠加 · 车道请求带 Bearer · `/api/cli` 仅在无 Bearer 时绑定 active  
> **防误伤**：无执行人 / 空禁用列表 / 未知能力 → 不拦；不用「别人的 active」误拦当前 HTTP 操作者  
> **不包含**：自定义角色模板矩阵、部门组织树、企业 SSO / AD、公网多用户引擎、物理删除账号、把身份做成 `features/` 热插拔包

**关联**：  
[企业Token用量汇总方案.md](./企业Token用量汇总方案.md) §5（本机登录身份）·  
[企业级安全加固方案.md](../安全/企业级安全加固方案.md) ·  
`.cursor/rules/workbuddy-ops-standard.mdc`（身份属控制面，不进业务 Cordis）

## 1. 一句话总结（给非技术人员）

现在谁能登录 WorkBuddy，多半靠装好时自带的演示账号。本方案要让**管理员在聊天壳账号菜单里点「人员」**，打开一张表，自己加人、停用、改「是不是管理员」、帮人重置密码。做成之后：同事有账号就能在 **3081** 登录用；不是管理员的人看不到这张表，也看不到全公司用量。

---

## 2. 加在哪 · 加了有什么效果（大白话）

### 2.1 界面放哪

| 位置 | 谁看得见 | 做什么 |
|------|----------|--------|
| **3081** 右上角 / 侧栏 **账号菜单** | 仅 **管理员** | 多一项 **「人员」**（或「人员和角色」） |
| 点「人员」后打开的 **管理页** | 同上 | 一张账号列表 + 新增 / 停用 / 改角色 / 重置口令 |
| **成员** 账号菜单 | 普通成员 | **没有**「人员」项；仍可改自己密码（已有改密能力） |

管理页实现优先落在 **引擎 SPA `:8000`**（与配置中心、企业用量同级控制面页）；3081 只负责**入口跳转 / 嵌套打开**，不另造第二套用户库。

```text
打开 http://127.0.0.1:3081 并登录（admin）
    → 点账号菜单 →「人员」
    → 打开引擎人员管理页（:8000，带当前登录态）
    → 列表增删改停用 → 写回本机 users.json
```

### 2.2 做成之后的效果对照

| 以前 | 有了之后 |
|------|----------|
| 基本靠种子账号 `admin` / `hebo`，加人要改文件或找开发 | 管理员在页面上点几下就能加人 |
| 同事要用，得找人配环境 | 建好账号，告诉对方账号和初始密码，对方就能在 3081 登录 |
| 角色写在文件里，平时看不见 | 页面上能看谁是管理员、谁是成员 |
| 忘密码只能改库 | 管理员可重置临时口令，并要求下次登录改密 |

**五个日常场景：**

1. **加人**：填显示名、账号、初始口令、角色（成员 / 管理员）→ 对方可登录。  
2. **停用**：离职或口令外泄 → 不能再登录；历史用量仍挂原 `user_id`。  
3. **改角色**：把某人提成管理员（或降为成员）→ 立刻影响「能否看企业用量 / 人员页」。  
4. **重置口令**：给临时密码 + 标记必须改密 → 对方登录后改成自己的。  
5. **本人改密 / 改显示名**：成员也可改自己的（显示名可 P0 或 P0.1）。

## 3. 现状（已经有什么）

| 能力 | 落点 | 说明 |
|------|------|------|
| 本机用户库 | `engine/app/auth/users.py` → `engine/data/.../users.json` | 账号、显示名、`role`、`disabled`、`must_change_password`、scrypt 哈希 |
| 种子账号 | `admin`（管理员）、`hebo`（成员） | 仅文件不存在时写入 |
| 登录 / 我 / 改密 / 退出 | `/api/auth/login` · `/me` · `/change-password` · `/logout` | 3081 挡板 + 引擎页共用 |
| 角色实际生效点 | 企业用量等接口要求 `role=admin` | 见 `/api/usage/enterprise/*` |
| 停用库函数 | `set_user_disabled` | **尚无**对外管理 API / UI |
| 列表公开信息 | `list_public_users` | 给企业用量补零行用，**不是**管理页 CRUD |

结论：**身份骨架已在**；缺的是「管理员可操作的人员维护面」与对应 HTTP，不是另起一套组织权限系统。

## 4. 目标与边界

### 4.1 产品目标（P0）

1. 管理员能在 UI 上完成：列表、新增、停用/启用、改角色、重置口令。  
2. 角色仅两个内置值：`admin` / `user`（展示名：管理员 / 成员）。  
3. 成员看不到人员入口；非管理员调管理 API → 403。  
4. 系统至少保留 **1 个未停用的管理员**（禁止把自己锁死）。  
5. 不做物理删除（避免用量 `user_id` 变孤儿且无法审计）。  
6. 引擎仍只绑回环；口令不进日志、不进响应明文（重置接口仅在创建/重置时**一次性**回传临时口令给管理员，或仅让管理员手填后自行转告）。

### 4.2 明确不做（本阶段）

| 不做 | 原因 |
|------|------|
| 自定义角色 + 权限勾选矩阵 | 当前除企业用量外几乎无第二处读 `role`；矩阵无处生效 |
| `features/people` 热插拔包 | 身份是控制面；关掉 feature 会导致登录/用量归户失效（与企业用量方案 §5.2 一致） |
| 第二个 bridge / 正式 Cordis 业务包 | 铁律 |
| 引擎 `0.0.0.0` + 自造公网 Token | 安全方案禁止；企业 SSO 单独立项 |
| 部门 / 岗位 / 组织树 | 无业务刚需，先不做 |
| 自助注册开放给全员 | 可选 P1；P0 仅管理员创建 |
| 聊天一句话直接改账号且无页面确认 | 高敏操作以管理页为准；Agent 只读查询可后续加 |

### 4.3 可行性结论

| 维度 | 结论 |
|------|------|
| 技术可行性 | **高**。用户库、哈希、停用、角色字段、admin 校验均已存在；主要是补 API + 引擎页 + 3081 菜单入口。 |
| 产品可行性 | **高**。场景清晰，直接解决「谁能登录、谁是管理员」。 |
| 架构合规 | **可行**。落 `engine/app/auth/` + 引擎 SPA；3081 仅入口；不进 `features/`。 |
| 主要风险 | 最后一个管理员被停用/降权；重置口令明文短暂暴露；与企业用量「按人」口径需保持同一 `user_id`。 |

**建议：按本方案做 P0，角色目录化留到有第二种真实权限检查点时再做。**

## 5. 角色模型（P0 写死 · P1 可演进）

### 5.1 P0（推荐立刻做）

| 角色 id | 展示名 | 能力 |
|---------|--------|------|
| `admin` | 管理员 | 企业用量、人员维护、（已有）其它 admin 门禁 |
| `user` | 成员 | 聊天、个人用量、写码等日常能力；无人员页、无企业用量 |

写入字段仍是用户行上的 `role` 字符串，与现网一致。

### 5.2 P1（有第二种权限时再做）

把角色收成小目录（如 `roles.json`：内置不可删），人员只引用 `role_id`。  
权限点仍在引擎各接口逐个判断（如 `usage.enterprise`、`users.manage`、`deploy`…），**不做**大勾选矩阵 UI，除非业务明确要求。

## 7. 接口草案（中文 tags「账号」）

一律：有效 Bearer + `users.json` 中 `role=admin` 且未停用。  
响应禁止回显 `password_hash`。

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/auth/users` | 列表（含 `disabled`、`created_at`、`must_change_password`；可含已停用） |
| `POST` | `/api/auth/users` | 新增：`username`、`display_name`、`password`、`role` |
| `PATCH` | `/api/auth/users/{id}` | 改 `display_name` / `role`；可选改其它非密字段 |
| `POST` | `/api/auth/users/{id}/disable` | 停用（或 PATCH `disabled=true`） |
| `POST` | `/api/auth/users/{id}/enable` | 启用 |
| `POST` | `/api/auth/users/{id}/reset-password` | 重置口令：管理员提供新口令，或服务端生成临时口令；置 `must_change_password=true` |

**硬规则（服务端必须校验）：**

1. `username` 唯一（大小写不敏感）、合法字符集（与现 `_user_id_for` 策略一致）。  
2. 新密码长度 ≥ 8（与现改密一致）。  
3. `role ∈ {admin, user}`。  
4. 停用或降权后，未停用 `admin` 数量 ≥ 1。  
5. 禁止管理员停用/降权「当前唯一管理员」；禁止删除自己导致无管理员（P0 无删除则重点卡停用/改角色）。  
6. 引擎 host 仍 ∈ `{127.0.0.1, localhost, ::1}`。

库函数建议在 `users.py` 增补：`create_user`、`update_user`、`reset_password`（`set_user_disabled` 已有可复用）。

## 8. UI 草案

### 8.1 列表列

显示名 · 账号 · 角色 · 状态（正常 / 停用 / 待改密）· 创建时间 · 操作

### 8.2 操作

- **新增**：弹层表单。  
- **改角色**：下拉确认。  
- **停用 / 启用**：二次确认文案。  
- **重置口令**：确认后展示一次性临时口令（或管理员自填），关闭后不再回显。

### 8.3 3081 入口

在现有账号菜单（`mes-bridge` client-src 设置/账号区，与「用量」并列逻辑）中：

- `authUser.role === "admin"` 时渲染「人员」；  
- 点击 → 打开引擎人员页（同域/同回环，带 token）；  
- 非 admin 不渲染，且深链访问引擎页时 API 仍 403。

## 10. 验收清单

### 10.1 产品 / 人工

1. 用 **admin** 登录 **3081** → 账号菜单有「人员」→ 能打开列表。  
2. 用 **成员** 登录 → **无**「人员」；直接调管理 API → 403。  
3. 新增成员账号 → 对方在 3081 登录成功；个人用量归到新 `user_id`。  
4. 停用该账号 → 登录失败；历史用量行仍在（企业用量视角）。  
5. 把某成员改为管理员 → 可见企业用量与人员入口。  
6. 重置口令 → 临时口令可登录，且要求/可完成改密。  
7. 尝试停用最后一个管理员 → **失败**并有中文提示。  

### 10.2 技术

```bash
# 引擎侧单测（实施后补齐用例名，示例）
python -m unittest tests.test_auth_users_admin -v

# 探活仍认引擎
curl -sf http://127.0.0.1:8000/api/runtime
```

- `scripts/check-secrets.sh` 不出现明文口令进库。  
- 不新增 `features/` 身份包；不改 DSH 插件源码。  
- 产品入口话术仍写 **3081**；API/管理页验收写 **8000**。

## 11. 风险与对策

| 风险 | 对策 |
|------|------|
| 唯一管理员被停用/降权 | 服务端硬校验未停用 admin ≥ 1 |
| 重置口令被旁人看见 | 一次性展示；日志脱敏；本机回环降低远程窃听面 |
| 与企业用量串账 | 新建用户 `id` 稳定（现有 `u_<username>` 规则）；禁止复用已停用 username 除非产品明确允许（建议 P0：**停用后用户名仍占用**） |
| 做成 feature 被关掉 | 本方案禁止；身份只在引擎 |
| 聊天误操作改账号 | 写操作以管理页为准；Agent 若加工具仅 list |

## 14. 落地对照（P0）

| 项 | 落点 |

| 用户库 CRUD + 至少一管理员 | `engine/app/auth/users.py`（`create_user` / `update_user` / `reset_user_password` / `set_user_disabled`） |
