# 一体化「需求→上线」优化方案（测环境 · 全自动）

> **状态**：方案稿（先对齐产品，不写代码）  
> **冻结日口径**：主路径 1～10 已验收 LOCKED；本方案只加固「无人值守 + 测环境」，不推倒编排。  
> **产品一句话**：贴需求/图 → **中间不需人工确认** → 自动跑完 → **上到测试环境**（不是生产）。

相关文档：[需求到上线一体化方案](./需求到上线一体化方案.md) · [企业级安全加固方案](../安全/企业级安全加固方案.md) · 部署探活 LOCKED（`.cursor/rules/workbuddy-deploy-service-alive.mdc`）

---

## 1. 我们要什么 / 不要什么

| 要 | 不要 |
|----|------|
| 全流程自动化，中间不弹确认 | 写码/提交/PR/部署逐步点头 |
| 终点是**测试环境** | 一键直捅生产 |
| 挂了能发现、能回滚、能看懂 | 「拷完文件」就算成功 |
| 半截失败说清楚（标黄/停住） | 假绿继续装成功 |
| 事后能查是谁跑的哪一次 | 用中途人工闸门换「安全感」 |
| 生产另开通道（以后再说） | 把生产审批塞进现在这条主路径 |

**和「传统企业审批流」的区别**：  
本产品的企业感 = **环境锁死 + 自动可靠 + 可观测 + 可追溯**，不是流水线中途人工批准。

---

## 2. 现状（已经对齐产品的部分）

这些**已经符合**「测环境全自动」，不要当成缺口去改掉：

1. 默认 `dev_pipeline.auto_run: true`：begin 后 1→10 连跑，中间无 pipeline 确认按钮。  
2. 硬步骤可由流水线代签/直调工位（为的是不停顿）。  
3. 部署侧配置意向已是测环境：`code_deploy.default_env: staging`、`env_whitelist: [staging]`、`allow_production: false`（见 `config.example.yaml`）。  
4. 探活失败必须回滚（LOCKED）；空变更硬失败、fix ≤3 轮；一张卡一本账。  
5. 写码复用插件 Job，审/提/部署复用四车道，不另造第二套引擎。

**真正要补的**，是让「无人值守」更稳、更敢交给测试环境，而不是加确认点。

## 3. 优化方向（按优先级）

### P0 · 环境锁死（防误上生产）

**目标**：一体化步骤 10 **只能**打到测试/staging；配置或调用想碰生产 → 直接拒绝，并在时间线写明原因。

**建议做**

- 产品文案统一：「需求→上线」= **上到测试环境**（聊天、卡标题、Receipt、手册）。  
- 引擎硬校验：pipeline 触发的部署走 `env_whitelist`；`allow_production: false` 时拒绝 production。  
- 配置样板：企业/发版默认只含测试入口（host / health_url / ssh_app_path），与生产清单分离。  
- 验收：故意配生产 env → 步骤 10 失败且不触达生产机。

**不做**：为「安全」在步骤 5/8/9/10 中途加人工确认。

---

### P0 · 无人值守要「停得明白」

**目标**：中途不用人点头，但失败时人一眼知道卡在哪、能不能重试、有没有半成功。

**建议做**

- **禁止静默假绿**：提交超时软跳过、PR skip、部署未跑 → Run 终态必须是 `failed` 或 `partial`，Summary **标黄/标红**，列出未完成步。  
- **partial 默认不部署**：例如 1～8 过了、9 开 PR 失败 → 标黄并停；是否「无 PR 也允许部署到测环境」做成显式配置（默认建议：测环境可配置允许，但必须写进 Summary，不能假装全绿）。  
- **可恢复**：时间线「重试本步 / 从失败步续跑」；同会话追问 = 新开独立任务但带上一任务上下文（已有方向，保持）。  
- **验收**：人为让提交或 PR 失败 → 界面不是全绿成功；日志有原因。

---

### P1 · 自动更稳（少因配置空、抖动而停）

**目标**：少出现「必须人去填一句/点一下才能继续」——那是自动化缺口，不是要加审批。

**建议做**

1. **验证命令**：`validate_commands` 给测环境项目填真实命令模板；空清单时步骤 6 明确 `waiting_user` 并指引去配置，**禁止空清单当 PASS**。  
2. **部署抖动**：保持 `max_deploy_attempts`（已有）；探活空窗/SSH 抖动自动重试，硬失败才停。  
3. **PR 策略与测环境一致**：  
   - 测环境交付是否**必须**开 PR，做成配置（例如 `pr_required_for_success: false` 时，skip PR 可为 partial 或仍允许部署，但文案写清）。  
   - GitLab/GitHub 识别失败 → 明确 skip + 指引，不算静默成功。  
4. **工作区默认**：默认工程目录配置齐全，减少「选错目录导致整单挂」。  
5. **验收**：目标演示仓从贴图到测环境入口变绿，中间零确认、零手工填表（配置事先备好）。

---

### P1 · 可观测与事后审计（不打断流程）

**目标**：人不用点确认，但要能汇报、能追责。

**建议做**

- Run Summary / Receipt 固定字段：需求摘要、改动文件数、验证结果、审码结论、提交/PR 链接或 skip 原因、**测试环境入口 URL**、探活结果、是否回滚。  
- 审计落盘（后台）：`user_id`、run_id、每步起止、终态、部署 env=staging；**不**要求中途 nonce 确认。  
- 过程流关键信息脱敏（Key / Token 不进 SSE）。  
- 验收：跑完一单，Summary 可直接贴给测试同事当交接。

---

### P2 · 生产另册（明确不进本主路径）

**目标**：以后真要上生产，不污染现在的测环境全自动。

**建议做（仅预留，本阶段不实现）**

- 独立「生产发布」能力或开关：默认关；打开后才允许 production，并走审批/双人（另立项）。  
- 文档写死：一体化主路径 **永不**默认生产。  
- 不做：把生产 HITL 塞进当前 1～10 自动连跑。

## 4. 阶段怎么排（仍不写代码时的实施顺序）

```text
① 文案 + 环境锁死（测环境 only）
        ↓
② 假绿治理（partial/失败说清楚；默认策略与「可否无 PR 仍部署测环境」拍板）
        ↓
③ 配置样板（validate、部署、默认工作区）让演示仓零打断
        ↓
④ Summary/审计（给人看、事后查）
        ↓
⑤ 生产通道另立项（有需要再说）
```

---

## 5. 需要产品拍板的 3 件事

1. **开 PR 失败时**：测环境还让不让继续部署？  
   - A：必须先有 PR/MR 才部署（更严）  
   - B：测环境允许无 PR 直接部署，但 Summary 标黄（更顺自动化）  
2. **验证步没有命令时**：硬停等人配，还是可配置跳过验证（跳过必须标黄）？  
3. **成功定义**：测环境探活 200 + 入口可打开 = 成功；是否还要求「远端已有 commit/PR」才算绿？

（建议默认偏自动化：1-B、验证空则硬停促配置、成功以测环境探活为准并在 Summary 列出 Git/PR 状态。）

---

## 6. 明确不做的事（避免再跑偏）

- ❌ 为「企业级」在写码/提交/PR/部署中途加确认卡  
- ❌ 把 `require_hitl_steps` 做成默认打断全自动  
- ❌ 推倒 10 步或另造第二套一体化  
- ❌ 改写码插件仓「顺便做流水线」  
- ❌ 关闭部署探活/回滚  
- ❌ 空 `changed_files` 当成功  

---

## 7. 一句话结论

一体化要打磨的是：**测环境无人值守流水线**——锁死环境、消灭假绿、配齐自动依赖、跑完可交接；  
**不是**把流水线改成逐步审批。生产发布以后单独立项，不塞进这条主路径。
